> 目标：**8 分钟内讲完**，让面试官记住一句话，并能顺着任意一个追问往下深挖。
> 全程只需要一个命令和五个提问；不需要改代码。

## 0. 一句话开场（20 秒）

> "这是一个订单管理服务，客户可以用自然语言让 AI 助手查订单、下单。**核心不是'接上了大模型'，而是接上之后怎么保证它不闯祸**：模型只能选商品和数量，金额由服务端定；任何会改数据的操作都只生成一张卡片，客户点确认才执行——因为**模型的输出是不可信输入**。"

按这个顺序讲，面试官的问题会自动落在你准备过的地方。

## 2. 五个提问，五次亮点

界面顶栏可以改「当前客户」，用 **1001** 和 **2002** 两个身份演示。

| # | 你输入 | 屏幕上会发生什么 | 你要指出的一句话 |
|---|---|---|---|
| 1 | 「我有哪些订单？」 | 助手返回订单列表 | 只读工具**直接执行**：查的是 `X-Customer-Id`，模型没有传客户 id 的能力，越权在类型上就不可能 |
| 2 | 「帮我下单 3 个 Widget」 | 出现**待授权确认单**：`创建订单：WIDGET-01 × 3`，单上列「商品 WIDGET-01 / 数量 3」，带「授权执行 / 拒绝」 | 注意 sku 是 `WIDGET-01` 不是 `Widget`——模型一开始会瞎编，我用 catalog 给它做了 grounding（ADR-0006）。**现在什么都不执行**，去订单页看，单数没变 |
| 3 | 点「授权执行」 | 卡片变 CONFIRMED、落一枚「已执行」印章；订单页多出 `¥59.70`（3 × 19.90，单价由服务端解析） | 点第二次不会重复下单：卡片状态机 + 行锁 + 幂等键，三道 |
| 4 | 把「当前客户」改成 `2002` | 侧栏空、订单页空 | 所有查询都按客户收窄；他也没有 1001 的那些 token |
| 5 | 改回 1001，再问「我刚才说要下单几个？」 | 答 `3` | 这是**多轮记忆**：按 Conversation 隔离、落库、只回填该会话最近 20 条 |

**加演（20 秒）**：「新对话」→ 换个说法下单 → 点「拒绝」→ 卡片变 REJECTED 且订单页干净。

## 3. 如果面试官说「给我看看代码」

按这个顺序打开，每处都对应一个已被问过无数遍的坑：

1. **`assistant/application/AssistantService.java`** — 编排。
   - 它不是 `@Transactional`：**AI 调用绝不进事务**（ADR-0002）。
   - 只读工具在这里执行；变更工具**只**调用 `propose()`——这个类里根本没有执行变更 handler 的路径。
2. **`assistant/infrastructure/ai/SpringAiAdapter.java`** — `internalToolExecutionEnabled(false)` 是审批闸口：关掉 Spring AI 的自动执行，工具调用原样交回来自己分类。
   - 末尾 `systemPrompt()` 每次请求把 catalog 拼进去——这就是 grounding。
3. **`assistant/application/ActionConfirmationService.java`** — `SELECT ... FOR UPDATE` + 状态机，两次并发确认只执行一次。
4. **`infrastructure/ai/tools/OrderToolDefinitions.java`** — 白名单。注意 `createOrder` 的 schema 里**只有 sku 和 quantity，没有价格字段**。
5. **`idempotency/application/IdempotencyGuard.java`** — 幂等靠 **INSERT 撞唯一键**，不是先查后写；命中 COMPLETED 直接重放存储的响应（连模型都不再调）。
6. **`db/migration/V1__init.sql`** — 一份标准 SQL 直接建目标 MySQL 8；刻意不写 `ENGINE`/`CHARSET`/`ON UPDATE`/内联 `KEY`，脚本干净到可以在任何 MySQL 上重放。

## 4. 高频追问与答法

**Q：为什么不直接让模型调用工具（`internalToolExecutionEnabled(true)`）？**
因为那样"执行"发生在框架内部，我拿不到决定权。关掉它，工具调用回到我手里，我按白名单的 `mutating` 标志分流——只读的当场执行，变更的落卡片。**审批闸口必须在我这侧，不能指望模型自律。**

**Q：模型瞎编商品编号怎么办？**
实测过：让它下 3 个 Widget，它返回 `{"sku":"Widget"}`，而真实 sku 是 `WIDGET-01`，参数校验直接拦下。修法是每次请求把当前 catalog 拼进 system prompt（ADR-0006）。另一条兜底是"宁可失败也不猜"：sku 不在目录里就 400，绝不"帮它猜一个"。

**Q：价格能由模型给吗？**
不能，schema 里根本没有价格字段，`OrderService` 从 `catalog_items` 解析单价并算总价。模型能影响的只有"买什么、买几件"。

**Q：重复点击确认会下两单吗？**
不会。确认在事务里先 `SELECT ... FOR UPDATE` 锁行，再查状态；并发的第二次阻塞在锁上，拿到锁时状态已是 CONFIRMED，于是走重放分支。加上 domain 层的 `resolve()` 只允许从 PENDING 流转一次。

**Q：客户端超时重试呢？**
带请求头 `Idempotency-Key`，走 `idempotency_records`：`(customer_id, operation, key)` 唯一，用 INSERT 占位；COMPLETED 就重放原来的响应体，模型调用不会发生第二次（集成测试里断言了两次调用的 token 数完全相同）。键相同但请求体不同 → 409，因为这是键被挪用。如果进程在"动作已提交、标记未写入"之间挂掉，键会卡在 IN_PROGRESS，由 `IdempotencySweeper` 在保留窗口（默认 24h）过后刷成 FAILED，从而可用原键重试。

**Q：模型调用自己的超时和重试呢？**
超时是显式配的：同步调用通过 `RestClientCustomizer` 把 HTTP 客户端换成带超时的 `JdkClientHttpRequestFactory`（连接 5s / 读取 60s），流式用 Reactor `.timeout` + `.blockLast` 双上界。重试**不是我们写的**——Spring AI 1.1.8 自动给阻塞调用套了一层 `RetryTemplate`，默认 10 次、退避上限 3 分钟，一个卡死的上游最坏能被拖近 19 分钟；我们只用 `spring.ai.retry.*` 把它收到 **3 次 / 1s / ×2 / 上限 8s**。它只作用于阻塞调用（流式不被重试），也不支持 jitter。**这块没有自动化测试**——要断言就得引入假上游，我们选择靠真上游冒烟 + 日志观察。

**Q：为什么幂等表单独建，不放 `orders` 上？**
`client_request_id` 放订单表意味着每个业务聚合都要带一份技术簿记，而且对"查订单"这种操作根本无处安放。独立表是通用的（ADR-0005）。

**Q：AI 调用放事务里有什么问题？**
事务会一直握着数据库连接等一个几秒级的网络调用，连接池很快被打满；而且"AI 成功但本地回滚"会让两边状态不一致。所以顺序是：事务外调模型 → 短事务写业务表。变更操作干脆等确认后再执行，天然规避。

**Q：为什么不用 H2（或内存库）跑测试？**
曾经用过，后来**彻底去掉**：H2 的 `MODE=MySQL` 是翻译层不是 MySQL，会放过真 MySQL 会拒绝的写法，等于替我们把 bug 藏起来。现在本地开发、测试、交付全部跑同一套真实 MySQL 8——就是 `docker-compose.yml` 里那个常驻容器，测试连独立库 `ordermgt_test`、每次 `clean`+`migrate` 重建 schema。代价是跑测试前容器必须在，换来的是"测试里过了，目标库就真的过了"。当年 H2 放行、MySQL 报 1067 的那个迁移缺陷，就是这么被抓出来的（见 §5）。

**Q：为什么 `@Transactional` 在 service 层？**
因为事务边界是**用例**边界，不是数据访问边界。DAO 层只管一条语句，service 层才知道"建单 + 写明细"必须一起成立。

**Q：为什么要 Conversation 表，不直接把历史塞进 prompt？**
记忆需要边界和寿命。Conversation 是记忆的边界（"新对话"= 新建一行），Message 是内容；只回填该会话最近 N 条。这也让"回看历史"免费得到。

**Q：这个设计最脆的地方是哪里？**
两点，都很明确：一是**幂等键在"动作已提交、标记未写入"之间崩溃会卡在 IN_PROGRESS**——现在有 `IdempotencySweeper` 兜底（过期仍 IN_PROGRESS 的刷成 FAILED 可重试），但清理粒度是整个保留窗口（默认 24h），窗口内该键仍会被 409 拒绝；二是只读工具的结果目前是内联进助手消息回灌给模型的，正式版应该改成"工具结果回灌后让模型总结成自然语言"。

## 5. 关于本机 Docker（如果被问到"环境怎么搞的"）

容器现在是**真的跑起来了**：`colima` + QEMU，Docker Engine 29.5.2（linux/amd64），`docker compose up --build` 起 `mysql` + `app` 两个容器，MySQL 8 建库 → Flyway 建表 → health=UP → 下单/幂等/SPA 全通。过程中四个坑，前三个是环境，第四个是代码：

1. **brew 装不了**：Monterey x86_64 上 colima 没有 bottle，brew 退化成源码编译 go/qemu，以小时计。改用 MacPorts（`/opt/local`，`sudo port install`）。
2. **VM 镜像下不动**：`github.com` 的 release 302 跳转解析超时，下载只有 ~26 KB/s。改用 GitHub 代理（`gh-proxy.com`，~3 MB/s），342 MB 三十秒下完。
3. **镜像摘要对不上**——注意这**不是**文件损坏。colima v0.10.3 内嵌 `amd64-docker` 的摘要 `27652801…`，而 GitHub API 对同一 URL 现在报 `4cd967d2…`，我们下到的文件正好是后者：`colima-core` v0.10.4 的发布物被重新上传过，colima 里那份摘要过期了。解法是 `--disk-image <本地文件> --force-disk-image`——`--force-disk-image` 本来就是给"支持这个镜像、但摘要对不上"准备的。另外 Docker Hub 也不可达，给 VM 内的 Docker 配了国内 registry mirror。
4. **真代码缺陷（这个才是重点）**：容器一起来就挂，Flyway 报 MySQL **Error 1067 `Invalid default value for 'created_at'`**。根因是脚本里 `TIMESTAMP(3)` 列的默认值写成裸 `CURRENT_TIMESTAMP`（精度 0），而 MySQL 要求两者一致。全部改成 `CURRENT_TIMESTAMP(3)` 后通过。（当时还在用 H2 当本地库，H2 的 `MODE=MySQL` 对这个写法照单全收——这正是后来彻底去掉 H2、只跑真 MySQL 的直接原因。）顺带还修了一个：模型调用失败时接口返回 500 `INTERNAL_ERROR`，而错误码表里那个 `UPSTREAM_AI_ERROR(502)` 从没被抛过——Key 过期被报成了"我们的 bug"。

> 讲解时可以直接把这四点当"我为什么坚持要真跑一遍"的论据：第 4 条如果没在容器里跑，交付到面试方机器上第一次 `up` 就会失败。

## 6. 诚实清单（主动说，比被问出来强）

- 容器里的模型调用**没带真 Key 跑过**：容器化本身（构建、MySQL、迁移、接口、SPA）都验证了，DashScope 的网络可达性也验了（未带 Key 返回 401 而非超时），但"容器内跑通一次成功的模型往返"需要真 Key，我没把它写进任何脚本或文件。
- `ai_invocations` 每次调用都写一行（成功与失败，失败带 `ERROR`/`TIMEOUT`），但**没有读取端点**，审计全貌需要用 SQL 查；接口里只回带了 `model`/`latencyMs` 供界面显示耗时。
- SPA 已接上 SSE（`fetch` + `ReadableStream` 增量渲染），命令行/脚本走 JSON 接口；SSE 端点本身不做幂等。
- 模型调用有退避重试，但**是 Spring AI 默认机制**（我们只把参数收到 3 次 / 1s / ×2 / 上限 8s），**没有自研退避、没有 jitter、也没有为超时/重试写自动化测试**。
- 幂等键的超时清理任务有了（`IdempotencySweeper`，默认 60s），但清理粒度是保留窗口（默认 24h）。
- compose 只起单实例应用；确认态并发去重靠数据库行锁（多实例成立），但没压测过。

> 主动报缺口不会扣分；被问出来又说不出边界会。
