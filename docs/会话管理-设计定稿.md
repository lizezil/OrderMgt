# 会话管理：设计定稿

> 本文是「会话管理」这一能力的设计定稿，覆盖多会话并行、会话状态展示、会话归档、对话终止、对话恢复、对话队列。
> 它是一个**在原项目上落地的加分项延伸**（对应 [用户故事.md](用户故事.md) 的 P1 范畴），不改变核心确认闭环（E1）。
> 术语以 [CONTEXT.md](../CONTEXT.md) 为准；决策依据见 [docs/adr/](adr/) 下的 0011–0014；运行与接口全貌见 [README.md](../README.md)。

## 0. 范围与前提

- **使用者：客户自助，单租户。** 一切仍按会话客户收窄（登录态来自会话 cookie，见 [设计定稿 §8](面试作业-设计定稿.md)），不引入客服/运营控制台，不引入 `customers` 表或角色概念。
- **守住 ADR-0009。** 所有新增状态都待在 **Run 层**，**绝不**回到 Message 层；断线仍然只停投递、不停回合。
- **单实例假设。** 运行态注册表与状态总线都在进程内；多实例下的行为明确记为已知缺口，不假装支持。

## 1. 术语

核心运行期概念是 **Run**（一次执行实例），定义见 [CONTEXT.md](../CONTEXT.md)：

**Run**：一条客户消息触发的一次「准备 → 模型调用 → 落库」，也是**停止、重订阅、队列**的粒度。同一 Conversation 至多一个处于 `RUNNING` 的 Run。_Avoid_: Session, Turn, Job, Task。

> 领域词是 **Run**，因此表名为 **`runs`**，接口路径为 `/runs/{runId}`；`Turn` 是 `Message` 的禁用同义词，不复用。

## 2. 状态模型（两层，别混）

| 层 | 载体 | 取值 | 是否持久 |
|---|---|---|---|
| **生命周期 status** | `conversations.status` | `ACTIVE` / `ARCHIVED` | **持久**（列已在） |
| **运行态 state** | 派生，不入库 | `IDLE` / `RUNNING` / `WAITING_APPROVAL` | 易失，每次读时算 |
| **Run 状态** | `runs.status` | `RUNNING` + 终态 `COMPLETED` / `FAILED` / `CANCELLED` / `INTERRUPTED` | **持久** |

- 运行态 `state` **派生**：该会话有活跃 Run → `RUNNING`；否则有未过期 `PENDING` 卡片 → `WAITING_APPROVAL`；否则 `IDLE`。
- `FAILED` **不**进运行态枚举——失败已有 `ai_invocations` 审计行，做成常驻状态只会吵。
- **不设 `QUEUED`**：排队不落库，没有 Run 行可标。

## 3. 数据模型

只新增一张表。`conversations.status` 与 `ai_invocations.outcome` 都是 `VARCHAR` 且**无 CHECK / 无枚举**，因此归档与 `CANCELLED` 两个新取值**零迁移**。

### 3.1 `runs`（新增，`V3__runs.sql`）

```sql
-- V3__runs.sql
CREATE TABLE runs (
    id              BIGINT        NOT NULL AUTO_INCREMENT,
    conversation_id BIGINT        NOT NULL,
    status          VARCHAR(16)   NOT NULL,          -- RUNNING/COMPLETED/FAILED/CANCELLED/INTERRUPTED
    error           VARCHAR(1000) NULL,              -- 失败/中断原因，宽度对齐 ai_invocations.error
    started_at      TIMESTAMP(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    ended_at        TIMESTAMP(3)  NULL,
    PRIMARY KEY (id),
    CONSTRAINT fk_run_conv FOREIGN KEY (conversation_id) REFERENCES conversations (id)
);
CREATE INDEX idx_run_conv_status ON runs (conversation_id, status);
```

> 时间戳精度 `TIMESTAMP(3)` 遵循 [ADR-0008](adr/0008-pin-timestamp-precision-in-migrations.md)。**库层不强制**「唯一 RUNNING」——MySQL 无 partial index，该不变量在运行态注册表里保证（见已知缺口）。

### 3.2 既有列的新取值（零迁移）

- `conversations.status`：新增 `ARCHIVED`（原只有 `ACTIVE`）。
- `ai_invocations.outcome`：新增 `CANCELLED`（原 `OK/ERROR/TIMEOUT`）。

### 3.3 出参扩展

`ConversationResponse` 现为 `(id, title, createdAt, updatedAt, lastMessageAt)`，**不含任何状态**。扩展为追加字段（不改既有字段）：

```java
public record ConversationResponse(
        Long id, String title, Instant createdAt, Instant updatedAt, Instant lastMessageAt,
        String status,     // ACTIVE / ARCHIVED
        String state,      // IDLE / RUNNING / WAITING_APPROVAL（派生）
        Long runId) {}     // 正在跑的 Run 的 id（非 RUNNING 时为 null）
```

> `runId` 是停止按钮与「切回来接着看」定位那条 Run 的把手，可空（非 RUNNING 时为 null）；状态流的 `snapshot` 沿用同一形状。

## 4. API 面

| 能力 | 端点 | 说明 |
|---|---|---|
| 列表（带状态） | `GET /api/assistant/conversations?includeArchived=true` | payload 增加 `status` + `state` |
| 归档 | `POST /api/assistant/conversations/{id}/archive` | 非静止（有 RUNNING Run 或未过期卡片）→ 409 |
| 恢复 | `POST /api/assistant/conversations/{id}/restore` | `ARCHIVED → ACTIVE` |
| 发起回合（流式） | `GET /api/assistant/conversations/{id}/stream?message=` | **已存在**；忙时**入队** |
| 发起回合（同步） | `POST /api/assistant/conversations/{id}/messages` | **已存在**；忙时 **409**（保幂等路径原子） |
| 停止 | `POST /api/assistant/conversations/{id}/runs/{runId}/stop` | 仅对 `RUNNING` 有效；幂等 |
| 重订阅运行中回合 | `GET /api/assistant/conversations/{id}/runs/{runId}/events` | 首帧快照（当前累积文本）+ `token` 增量 |
| 删排队项 | `DELETE /api/assistant/conversations/{id}/queue/{itemId}` | `itemId` 为内存态 id |
| 每客户状态流 | `GET /api/assistant/events` | 首帧 `snapshot` + `state`/`queue` 增量 + `ping` |

> 队列**只报告、不操作**：状态流负责把队列推给前端，改动走 `DELETE`（可测、幂等）。

## 5. 错误码增量

`shared/api/ErrorCode.java` 现无队列相关码，新增一个：

```java
QUEUE_FULL(HttpStatus.TOO_MANY_REQUESTS, "this conversation's queue is full"),
```

复用既有码，不另造：会话忙（同步入口）与归档被拒 → `CONFLICT`(409)；Run / 排队项不存在 → `NOT_FOUND`(404)；越权 → `FORBIDDEN`。

> 队列满记 **`429`** 而非 409——队列满属**容量**问题，409 是「状态冲突」，语义不同。

## 6. 配置项

沿用 `application.yml` 的 `assistant.*` 命名：

```yaml
assistant:
  run:
    queue-depth: 5                 # 每会话排队上限，超出 429
  events:
    heartbeat-ms: 15000            # 状态流心跳
    max-connections-per-customer: 4
```

## 7. 测试落点（L1–L6）

| 层 | 新增/扩展 | 断言要点 |
|---|---|---|
| **L1 领域** | Run 状态机；`Conversation.archive/restore`；派生 `state` 纯函数 | 非法流转被拒；`RUNNING→终态`；三值派生正确 |
| **L2 应用**（Mockito） | `ConversationService.archive` 拒绝非静止；Run 调度器；启动对账 | 忙时入队、`queue-depth` 上限、停止取消上游；残留 `RUNNING→INTERRUPTED` |
| **L3 API 契约**（MockMvc） | archive 409 / restore；stop 幂等；`QUEUE_FULL` 429；`/events` 首帧 snapshot | 首帧全量 + 增量；重订阅快照；同步入口忙时 409 |
| **L4 集成**（真 MySQL + 桩） | Run 落库与终态；重启对账；归档会话发送自动恢复 | 构造残留 `RUNNING` 断言被标 `INTERRUPTED`；状态流与真实变化对齐 |
| **L5 SPA**（Vitest） | store 收 `snapshot` 后 patch；重连替换快照；队列 UI | 徽标渲染；排队项可见且可删 |
| **L6 E2E**（Playwright） | 多会话并行、停止、归档/恢复、重连看状态 | 全程走 `offline` 桩 |

## 9. 已知缺口（诚实清单）

- **多实例**：运行态注册表与状态总线都在进程内，不跨实例；库层不强制「唯一 RUNNING」；启动对账在多实例下会**误伤**其他实例的活 Run。当前单实例运行，与 compose 一致。
- **公平性**：`assistant.stream.max-concurrent=20` 仍是**全局**上限，一个客户可开满 20 个 Run；**每客户并发配额未做**。
- **队列**：上限 5，突发时会 429；排队项不落库，重启即失。
- **无硬删除**：归档只增不减，数据永久保留；合规删除路径未开。
- **重订阅**：重连重发全量快照（换取零服务端事件缓存）；被中断的 Run 只能「重发新 Run」，不能续传。
- **前端**：无状态库（单例 composable），Pinia 仅作升级路径；E2E 仍只跑 Chromium、走 `offline` 桩。
