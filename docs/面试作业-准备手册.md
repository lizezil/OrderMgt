## 1. 一句话定位 + 原始要求逐条对照

### 1.1 背下来的那句话

> 「这是一个订单管理服务：客户用自然语言让 AI 助手**查**自己的订单，**并在确认后**才真正创建或变更订单。
> 核心不是『接上了大模型』，而是**接上之后怎么保证它不闯祸**——模型只能选商品和数量，金额由服务端定；任何会改数据的操作都只生成一张卡片，客户点确认才执行。**因为模型的输出是不可信输入。**」

这句话把面试官的注意力引到你准备最充分的地方：安全边界 + 一致性，而不是"我调了个 API"。

### 1.2 硬性要求（题目明示"必须具备"）逐条对照

| 原题要求 | 我的交付 | 讲的时候指哪 |
|---|---|---|
| **基础 API 接口**：提供 RESTful 接口 | `OrderController` / `CatalogController` / `AssistantController` / `ConversationController` / `ActionController` 共 5 个控制器，统一响应体 `ApiResponse` | `shared/api/ApiResponse.java`、Swagger |
| **AI 工具调用集成**：Function Calling | Spring AI 1.1.8 的 `ChatClient` + 工具白名单 `ToolRegistry`（5 个工具，只读/变更分类） | `assistant/infrastructure/ai/tools/OrderToolDefinitions.java` |
| **数据库交互 + 事务管理**：ORM + 事务 | MyBatis-Plus + Flyway 管 schema；`@Transactional` 只在 service 层、只包住 DB 操作 | `order/application/OrderService.java`、`assistant/application/ActionConfirmationService.java` |

### 1.3 核心考察的"三件事"逐条对照

| 原题核心点 | 我的做法（一句话） | 深挖入口 |
|---|---|---|
| **① AI 服务调用**：超时、异常、重试 | 同步连接 5s/读取 60s 显式超时；框架重试收窄到 3 次/1s/×2/上限 8s；流式仅在**首字节前**整条重放；失败归类 `TIMEOUT`/`ERROR`，对外 502 | `SpringAiAdapter.java`、`AiCallPolicy.java`、`AiHttpClientConfig.java` |
| **② 业务逻辑闭环**：AI 结果如何操作数据库 | 只读工具直接执行；**变更工具永不自动执行**，落 `PendingAction` 卡片，确认后才在事务里执行 | `AssistantService.java`、`ActionConfirmationService.java` |
| **③ 数据流转**：前端→业务→AI→解析→持久化→返回 | 见 §3 的「一次请求的完整旅程」 | 全链路 |

## 2. 项目结构：怎么讲"结构清晰"

### 2.1 分层与依赖方向（讲结构先画这张图）

```
        ┌───────────────────────────────────────────────┐
        │  api/          控制器 + DTO(record) + ApiMapper │  ← HTTP 边界
        └───────────────┬───────────────────────────────┘
                        │ 依赖
        ┌───────────────▼───────────────────────────────┐
        │  application/  用例编排 + @Transactional 边界   │  ← 事务边界
        └───────────────┬───────────────────────────────┘
                        │ 依赖
        ┌───────────────▼───────────────────────────────┐
        │  domain/       实体/值对象/端口，零框架依赖     │  ← 业务规则
        └───────────────▲───────────────────────────────┘
                        │ 实现端口
        ┌───────────────┴───────────────────────────────┐
        │  infrastructure/  MyBatis-Plus 持久化、Spring AI │  ← 技术细节
        └───────────────────────────────────────────────┘
```

一句话：**`api → application → domain`，`infrastructure → domain`（实现端口），domain 不依赖任何框架。**

### 2.2 六个包各干什么

| 包 | 职责 | 关键类 |
|---|---|---|
| `shared/` | 跨领域共享，不含业务规则 | `ApiResponse`、`PageResult`、`ErrorCode`、`GlobalExceptionHandler` |
| `config/` | 装配 | `MyBatisPlusConfig`、`OpenApiConfig`、`AsyncConfig`（流式线程池）、`AiHttpClientConfig`（超时） |
| `idempotency/` | 通用幂等组件（技术关注点，跨用例复用） | `IdempotencyGuard`、`IdempotencySweeper` |
| `catalog/` | 商品目录——**价格的唯一来源** | `CatalogRepository`、`CatalogController` |
| `order/` | 订单核心域 | `Order`(聚合根)、`OrderLine`、`OrderNumber`、`Money`、`OrderService` |
| `assistant/` | 助手领域：记忆、工具白名单、待确认动作、确认闭环、Run | `AssistantService`、`ActionConfirmationService`、`ConversationService`、`SpringAiAdapter`、`ToolRegistry`、`ConversationRunQueue` |

### 2.3 为什么"单模块 + 领域分包"，而不是微服务全家桶 / 多模块

这是原题埋的坑（坑位分析 A3）：技术清单里列了 Spring Cloud，却明说"单体演示即可"。

> 我的说法：「两天时间上 Nacos/Gateway/多模块，只会让主链路跑不通、讲解负担翻倍。所以我用**单 Maven 模块 + 按领域分包**：包的边界就是未来的服务边界，但今天不为它付出分布式代价。**领域分包让依赖方向可验证**——domain 包 import 里出现 `org.springframework` 就是违规。」

### 2.4 目录树（现场可以直接贴）

```
backend/src/main/java/com/example/ordermgt/
├── shared/       统一响应体、错误码、分页、全局异常处理
├── config/       MyBatis-Plus、OpenAPI、流式线程池、AI HTTP 超时
├── idempotency/  通用幂等（domain / application / infrastructure）
├── catalog/      商品目录（价格唯一来源）
├── order/        订单领域（Order 聚合根、状态机、事务边界）
└── assistant/    助手领域
    ├── AiCallPolicy     模型调用的超时/重试常量
    ├── domain/          无框架依赖：Conversation / Message / Run / PendingAction / ToolSpec / AiAssistantPort
    ├── application/     AssistantService、ConversationService、ActionConfirmationService、ConversationRunQueue、ActionCardFactory
    ├── infrastructure/  Spring AI 适配器(ai/)、MyBatis-Plus 持久化(persist/)、清理任务(schedule/)
    └── api/             控制器、DTO、ApiMapper

### 2.5 一处**刻意**的例外（主动说，显示你想过依赖）

`assistant/infrastructure/ai/tools/OrderToolDefinitions` 把只读工具接到 `order.application.OrderService` 上——这是 `infrastructure → application` 的一条边。

> 说法：「工具定义本质是**装配代码**（哪个工具名对应哪个业务用例），这条边是单向的：`order` 侧不反向依赖 `assistant`，不构成环。全仓仅此一处，且有注释说明。」

## 3. 实现细节：一次请求的完整旅程（讲顺这条 = 讲顺 80%）

以**流式入口**为例（它包含同步入口没有的排队/投递逻辑），从浏览器点击到 `done`：

| # | 发生了什么 | 代码位置 | 事务？ |
|---|---|---|---|
| 1 | 前端带 `X-Customer-Id` 起 `fetch`，读 `ReadableStream` 分帧 | `frontend/src/api.ts#chatStream` | — |
| 2 | 控制器**先校验归属**（越权的请求连"忙不忙"都不能知道），再进队列 | `ConversationController#stream` → `conversationService.getOwned` | 只读事务 |
| 3 | **排队**：该会话已有 Run 在跑就 FIFO 入队（深度 5，满了 429 `QUEUE_FULL`）；空闲则立刻起 | `ConversationRunQueue#submitStreaming` | 无 |
| 4 | `prepare`：拿到/新建会话 → **先把客户消息提交入库** → 组装最近 20 条记忆 | `AssistantService#prepare` | 三个短事务 |
| 5 | 开一条 `RUNNING` 的 `Run` 落库 | `AssistantService#executeTurn` → `runRepository.save(Run.start(...))` | 短事务 |
| 6 | **调模型（无事务！）**：流式增量通过 `onTextDelta` 逐字推给前端 `token` 事件 | `SpringAiAdapter#respondStreaming` | **无**（ADR-0002） |
| 7 | 模型返回后 `complete`：遍历工具调用**按 `mutating` 分流**——只读当场执行、变更落卡片 | `AssistantService#complete` | 若干短事务 |
| 8 | 回执 `done` 事件带与 JSON 接口**同构**的结果（含卡片）；关 Run 为 `COMPLETED` | `ConversationController#streamTurn` | 短事务 |
| 9 | 每次模型调用往 `ai_invocations` 落一行审计（成功/失败都写） | `AssistantService#recordSuccess/recordFailure` | 旁路，写失败只 warn |

**这条链路里能自然引出 5 个考点**，面试官顺着任意一步追问，你都有准备：

- 第 2 步 → 越权防护（§6）
- 第 3 步 → 会话级并发控制（§7）
- 第 4/6/9 步 → **AI 不进事务**、审计旁路（§4.2、§5）
- 第 5/6 步 → Run 层与"客户消息先落库"（§7）
- 第 7 步 → **审批闸口**（§4.1）

## 4. 五个"这道题真正在考的点"（每个都要能讲 3 分钟）

### 4.1 AI 输出是不可信输入 → 审批闸口（最重要，一定被问）

**题目原文的陷阱**：让 AI "决定调用哪个业务方法"。若直接把模型返回的函数名反射调用或拼 SQL，等于把控制权交给一个可被提示注入的模型。这是本题**最大的坑**。

**我的做法（三层）**：

1. **关掉框架的自动执行**：`ToolCallingChatOptions.builder().internalToolExecutionEnabled(false)`——工具调用原样交回来，我拿到决定权。
2. **白名单**：`ToolRegistry` 只注册 5 个工具（`queryMyOrders`/`getOrderByNumber` 只读，`createOrder`/`updateOrderStatus`/`cancelOrder` 变更）。模型返回未注册的工具名 → 直接 `UPSTREAM_AI_ERROR`。
3. **结构上就执行不了变更**：`AssistantService` 只调用只读 handler；变更 handler **只有 `ActionConfirmationService` 能调**——这个类里根本没有执行变更的路径。

> 追问「为什么不直接 `internalToolExecutionEnabled(true)`？」答：「那样'执行'发生在框架内部，我拿不到决定权。**审批闸口必须在我这侧，不能指望模型自律。**」

### 4.2 AI 调用绝不进数据库事务（ADR-0002）

**反例（不做会怎样）**：模型可能跑好几秒，事务里握着数据库连接等它 → 连接池被打满、锁等待、级联故障；而且"AI 成功但本地回滚"会让两边状态不一致。

**我的顺序**：事务外调模型 → 收获结果 → 短事务写业务表。
「AI 成功但本地失败」这类不一致，由**变更操作走"确认后执行"**天然规避——AI 阶段从不写业务表。

**谁有 `@Transactional`，谁没有**（这句话很长脸，背熟）：

| 有事务 | 没有事务 |
|---|---|
| `OrderService`（建单+明细一起） | `AssistantService`（含 AI 调用） |
| `ConversationService`（记忆读写） | `IdempotencyGuard`（它保护的动作可能含 AI 调用） |
| `ActionConfirmationService`（**可以**在事务里：确认路径只有建单/改状态，无网络调用，且要靠 `FOR UPDATE` 行锁去重） | `ConversationRunQueue`（纯内存） |

### 4.3 价格只有一个来源 + grounding（ADR-0006，有一个真实故事）

**规则**：模型只能给 `sku` 和 `quantity`；`createOrder` 的工具 schema 里**根本没有价格字段**；金额由 `OrderService#resolveLines` 从 `catalog_items` 解析。

**真实故事（讲这个最加分）**：实测让模型下 3 个 Widget，它返回 `{"sku":"Widget"}`，而真实 sku 是 `WIDGET-01`——**模型把商品名当成了 sku**。修法是每次请求把当前 catalog（sku/名称/单价）拼进 system prompt（grounding）；另一条兜底是"宁可失败也不猜"：sku 不在目录里就 400。

### 4.4 幂等有两条路，各司其职（ADR-0005 / 0007）

| 触发场景 | 机制 | 关键实现 |
|---|---|---|
| **客户端重试**（超时后重发） | `idempotency_records` 表，键 `(customer_id, operation, key)` | `IdempotencyGuard` 用 **INSERT 撞唯一键**占位，不是先查后写 |
| **重复点确认**（手滑点两次） | `pending_actions` 的**行锁 + 状态机** | `ActionConfirmationService` 的 `SELECT ... FOR UPDATE` + `PendingAction.adjudicate` |

**必须能说清的细节**：

- 命中 `COMPLETED` → **重放存储的响应原文**（连模型都不会再调一次——实测两次 `promptTokens` 相同，证明第二次是重放）。
- 键相同但请求体哈希不同 → 409（**键被挪用**）。
- 命中 `IN_PROGRESS` → 409（拒绝并发重复）。
- `FAILED` 允许用原键重试（`reclaim` 回 `IN_PROGRESS`，有竞态处理）。
- 「动作已提交、标记未写入」之间崩溃 → 键卡在 `IN_PROGRESS`，由 `IdempotencySweeper` 过期后刷成 `FAILED`；若连响应体都存不进 → `RESULT_UNKNOWN` 封印，绝不让重试再跑一次（会重复下单）。

### 4.5 解耦：AI 藏在端口后面（ADR-0003，对应加分项①）

- 业务只依赖 `AiAssistantPort.respond(customerId, List<ChatMessage> memory)`——**端口本身不知道"会话"存在**，它只收一串有序发言。
- `SpringAiAdapter`（`@Profile("!offline")`）实现真实调用；`MockAiAdapter`（`@Profile("offline")`，关键词驱动）供没有 Key 的演示，**集成测试复用它**（所以测试行为与演示一致，且不烧配额）。
- 这个端口带来的直接收益：**测试可以直接替换成桩**，不需要 mock 框架深处的东西。

## 5. 健壮性：超时 / 重试 / 审计（题目明示的考察点）

| 维度 | 做法 | 关键数字 |
|---|---|---|
| **超时（同步）** | `RestClientCustomizer` 换上带超时的 `JdkClientHttpRequestFactory` | 连接 5s / 读取 60s |
| **超时（流式）** | Reactor `.timeout()` + `.blockLast()` 双上界 | 2 分钟 |
| **重试（阻塞）** | **框架自带**的 `RetryTemplate`，用属性收窄 | 3 次 / 1s / ×2 / 上限 8s（默认是 10 次、上限 3 分钟） |
| **重试（流式）** | 自建同款退避，**仅首字节前整条重放**，首字节后不重试 | 3 次 / 1s / ×2 / 上限 8s |
| **失败归类** | 三种超时形态（Reactor/`SocketTimeout`/`HttpTimeout`）→ `TIMEOUT`，其余 → `ERROR` | 对外 502 `UPSTREAM_AI_ERROR` |
| **审计** | 每次调用写一行 `ai_invocations`（成功/失败都写），读取走 `GET .../invocations` | 旁路，写失败只 warn |

> 追问「为什么不重试到底 / 为什么没有熔断？」答：「重试会把已吐给客户的字再吐一遍，所以流式首字节后不重试。没有 jitter、没有熔断——**重复执行的风险由幂等键与卡片行锁兜住**，而不是靠重试策略。这是权衡，我写在已知缺口里。」

## 6. 安全与越权（演示价值最高的一块）

- **一切查询按 `X-Customer-Id` 收窄**：他人会话/订单返回 403 或按"不存在"（404），调用方**无法区分**"不属于我"和"不存在"。
- **模型没有传客户 id 的能力**：工具 schema 里没有 `customerId`，`queryMyOrders` 直接用手里的 `customerId`——**越权在类型上就不可能**。
- **卡片 token 绑定发起人**：24 字节随机 hex；知道 token 不够，必须同一请求里是**本人**（`isOwnedBy`）。
- **演示**：顶栏切 `1001`/`2002`，账目完全不同；`2002` 拿 `1001` 的 token 确认 → 403。

## 7. 会话与 Run 层（最近的扩展，讲的时候要标注"进行到哪"）

> ⚠️ **重要**：原题只要求"多轮记忆"，Run 层是**额外**做的。现场务必说清**哪些已交付、哪些是设计**，别把未实现的讲成已有。

### 已实现（可以演示/翻代码）

| 能力 | 实现 | 依据 |
|---|---|---|
| **Run 落库**：一次"发送→回复"= 一条 Run（`RUNNING`→`COMPLETED`/`FAILED`/`INTERRUPTED`），同步与流式共用一条执行回合 | `AssistantService#executeTurn`、`runs` 表（V3） | ADR-0011 |
| **会话状态派生**：侧栏徽标 `IDLE`/`RUNNING`/`WAITING_APPROVAL` 全部**从 Run + 卡片派生**，不入库 | `ConversationState.derive`、`ConversationService#listFor` | ADR-0011 |
| **重启对账**：启动时把库里残留的 `RUNNING` 标成 `INTERRUPTED` 并补 `ended_at`（一次性 `ApplicationRunner`，不是定时器） | `RunReconciler` | ADR-0011 |
| **忙时入队**：同一会话已有 Run 时，流式 FIFO 排队（深度 5 → 429），同步直接 409；排队项可删 | `ConversationRunQueue`、`DELETE .../queue/{itemId}` | ADR-0012 |
| **投递尽力而为**：客户端断线只停投递，回合照常跑完并落库 | `ConversationController#deliver/streamTurn` | ADR-0009 |

### 设计已定、**尚未实现**（如被问到，如实说"设计好了，还没落地"）

| 能力 | 设计要点 | 依据 |
|---|---|---|
| 停止运行中的 Run | `POST .../runs/{id}/stop`，真正 abort 上游，半截文本落成普通消息 | ADR-0012 |
| 归档 / 恢复会话 | 只归档"静止"会话（有 Run 或活卡片 → 409），不硬删 | ADR-0013 |
| 每客户状态流 | `GET .../events` 长活 SSE（快照 + 增量），走独立进程内总线，**不占回合池** | ADR-0014 |
| 重订阅运行中的 Run | 首帧当前累积文本快照 + `token` 增量 | ADR-0014 |

**一句话总结这段**：「Run 层把隐式的'发送→回复'变成有一行记录、有生命周期、能派生状态的东西；它没有违反 ADR-0009（Message 层没有状态列），而是在它之上加了一层。」

## 8. 数据库与迁移

三份迁移（Flyway，`backend/src/main/resources/db/migration/`）：

- **V1__init.sql**：`catalog_items`、`orders`、`order_lines`、`conversations`、`messages`、`pending_actions`、`ai_invocations`、`idempotency_records`
- **V2__orders_add_version.sql**：`orders.version`（乐观锁）
- **V3__runs.sql**：`runs` 表

**讲表的时候记住这几条"为什么"**：

| 表 | 一句话 |
|---|---|
| `catalog_items` | **价格的唯一来源**，5 条种子数据 |
| `orders` / `order_lines` | 聚合根 + 明细；幂等**不在这张表上** |
| `conversations` / `messages` | 记忆的边界与内容；"新对话" = 新建一行 conversation |
| `pending_actions` | 确认闭环的载体；`token` 是能力凭证；只存 `result_ref`（订单号），不存响应体 |
| `ai_invocations` | 审计旁路，给运维看（`messages` 给用户看） |
| `idempotency_records` | 通用幂等，键 `(customer_id, operation, key)` |
| `runs` | 一次执行的记录，`(conversation_id, status)` 索引撑住列表查询 |

> **一个讲出去很加分的细节**：`V1` 里 `TIMESTAMP(3)` 列的默认值必须写 `CURRENT_TIMESTAMP(3)`（精度一致），写裸的 `CURRENT_TIMESTAMP` 只有真 MySQL 才会报 1067——H2 的 `MODE=MySQL` 会放行。这正是本项目**彻底去掉 H2、全程真 MySQL** 的原因（ADR-0008）。

## 11. 高频追问与标准答法

| 追问 | 答法（要点） |
|---|---|
| 为什么不直接让模型调工具？ | 那样执行在框架内部，我拿不到决定权；闸口必须在我这侧 |
| 模型瞎编商品编号？ | 实测过（`Widget` vs `WIDGET-01`）；grounding + "宁可失败也不猜" |
| 价格能由模型给吗？ | 不能，schema 里没价格字段，从 `catalog_items` 解析 |
| 重复点确认会下两单吗？ | 不会，`FOR UPDATE` 行锁 + 状态机，第二次走重放 |
| 客户端超时重试呢？ | `Idempotency-Key` → `idempotency_records`，INSERT 占位，COMPLETED 重放 |
| 模型调用的超时和重试？ | 见 §5，注意主动说"重试是框架自带的，我只收窄参数" |
| 幂等表为什么不放 `orders` 上？ | 每个聚合都要带技术簿记，且"查订单"无处安放；独立表通用 |
| AI 调用放事务里有什么问题？ | 握连接等网络调用 → 连接池耗尽；且两边状态可能不一致 |
| 为什么不用 H2 跑测试？ | 它是翻译层不是 MySQL，会放过真库会拒的写法；当年就是这么漏掉 1067 的 |
| `@Transactional` 为什么在 service 层？ | 事务边界是用例边界；DAO 只管一条语句 |
| 为什么要 Conversation 表，不塞进 prompt？ | 记忆需要边界和寿命；也让"回看历史"免费 |
| 这个设计最脆的地方？ | 见 §12 诚实清单（主动报） |

## 12. 诚实清单（**主动说，比被问出来强**）

1. **退避是简版的**：流式仅首字节前重放，中途失败不重试；两处都无 jitter、无熔断。
2. **真实网络超时→退避的端到端没有假上游测试**：策略在单测里逐分支钉住，但没有真超时的集成断言。
3. **`MockAiAdapter` 是关键词驱动的桩**，只用于无 Key 演示，不理解真实语义。
4. **E2E 只跑 Chromium**，且助手走离线桩。
5. **前端两层测试未接入 CI**（仓库暂无 CI 配置）。
6. **Compose 只起单实例**：确认态并发去重靠行锁（多实例成立），但没压测；Run 的"唯一 RUNNING"不变量只在进程内保证，多实例会破。
7. **会话管理 04–07（停止/归档/状态流/重订阅）只有设计，未实现**（§7）。

> 主动报缺口不扣分；被问出来又说不出边界才扣。

# 起库 + 起应用（端口 8081）
docker compose up -d mysql

curl -s -X POST localhost:8081/api/assistant/chat \
  -H 'Content-Type: application/json' -H 'X-Customer-Id: 1001' \
  -d '{"message":"帮我下单 3 个 WIDGET-01"}'
curl -s -X POST localhost:8081/api/assistant/actions/<token>/confirm -H 'X-Customer-Id: 1001'
curl -s localhost:8081/api/orders -H 'X-Customer-Id: 2002'   # 看不到 1001 的单

make test-frontend   # L5，不需要 MySQL
make test-e2e        # L6，需先 make db-up
```

**常见故障预案**：
- 启动即失败 → 常驻 MySQL 没起（默认 profile `mysql`，连 `localhost:3306/ordermgt`）。
- `Migration checksum mismatch` → 改过已发布的迁移文件；`docker compose down -v && make db-up` 整卷重建。
- 助手调不通 → 没有 Key 或 Key 失效；切 `offline` profile 演示。

## 14. 可能被问、文档里没写的点（预案）

- **"为什么用 MyBatis-Plus 而不是 JPA？"**：题目两者都推荐；MyBatis-Plus 对"分页 + 手写 SQL + 行锁"更直接，`FOR UPDATE` 不用绕 JPQL。
- **"MapStruct 和 Lombok 怎么共存？"**：需要 `lombok-mapstruct-binding`，否则生成的 Mapper 找不到 getter/setter（已在父 POM 配好）。
- **"SSE 为什么用 `fetch` 不用 `EventSource`？"**：`EventSource` 不能设请求头，而每个请求都要带 `X-Customer-Id`。
- **"前端为什么不用 router / Pinia？"**：这个规模引入只会增加讲解负担；tab 切换一个 `ref` 就够。Pinia 记为升级路径。
- **"uptime / 可观测？"**：`/actuator/health`、`ai_invocations` 审计表、`GET .../invocations`。
