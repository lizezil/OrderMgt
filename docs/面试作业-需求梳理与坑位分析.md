# 后端研发工程师面试作业 — 需求梳理与坑位分析

> 说明：本文档由原始面试题目整理而来。
> 第一部分是**去掉宣传/流程性内容后的纯需求**；第二部分是**题目与实现中的"坑"分析**。

---

## 第一部分：需求精简版

### 1. 业务背景（与需求相关的部分）

- 业务为**企业级微服务架构**，支撑学习平台、AI 系统及多端 App 的数据交互与业务逻辑。
- 后续重点：**AI 与业务系统深度融合**。
- 对候选人的核心要求：不仅写好传统业务代码，还要能把 **AI 能力作为一种服务优雅地集成进现有系统**，并处理好 **AI 响应 与 本地事务 / 数据库操作 的一致性与逻辑闭环**。

### 2. 交付物

- 一个**结构清晰的 Spring Boot 后端模块**（单体架构演示即可，**不要求**完整微服务集群）。
- **必须**：Java 语言 + Spring Boot 框架。

### 3. 场景（三选一，也可自选）

| 选项 | 场景 |
| --- | --- |
| A | **智能助手集成**：假设 AI 团队已提供"意图识别服务"或"对话接口"，业务服务（订单管理 / 客服工单系统）根据 AI 识别的意图，自动执行业务代码（创建订单、查询数据库、修改状态等）。 |
| B | **文档摘要与归档**：接收文档内容 → 调用 AI 生成摘要 → 自动提取关键信息并存入数据库。 |
| C | 任意能体现"业务系统 + AI 集成"的场景。 |

> 重点：**不考察 AI 模型训练，考察后端架构与集成能力。**

### 4. 必须处理的三件事（题目明示的核心）

1. **AI 服务调用**：如何封装外部 AI 接口，处理**超时、异常、重试**。
2. **业务逻辑闭环**：AI 返回结果后，如何根据结果**操作本地数据库**。
3. **数据流转**：前端请求 → 业务层 → AI 服务 → 结果解析 → 数据持久化 → 返回前端。

### 5. 必须具备的能力（硬性）

1. **基础 API 接口**：提供 RESTful 接口供前端或其他服务调用。
2. **AI 工具调用集成**：通过 HTTP Client 或其他方式调用 AI 模型 API，实现 **Function Calling**（让 AI 决定调用哪个业务方法）或直接业务处理。
3. **数据库交互**：使用 JPA / MyBatis 等 ORM 框架，实现数据的持久化与**事务管理**。

### 6. 加分项

1. **架构设计**：分层清晰，体现"**AI 服务适配层**"与"**业务逻辑层**"的解耦。
2. **工程化实践**：统一异常处理、参数校验、日志记录、API 文档。
3. **流式响应**：AI 回复支持 **SSE**（Server-Sent Events）流式输出。
4. **容器化**：提供 **Dockerfile**，服务可一键 Docker 运行。

### 7. 约束条件

- 技术栈（推荐）：Java 17+、Spring Boot 3.x。
- 模型：使用 **qwen-max**（阿里云百炼 / DashScope）作为模拟的 AI 服务接口；API Key 由面试方提供，也可自选其他模型（其他模型需自行接入）。
- 时间：**2 天内完成**。

### 8. 真正的评估维度

> 项目结构、代码规范、异常处理、是否有 Bug、架构清晰度。
> （"不关心过程，只看最终成果演示"；且下一轮面试会围绕这份作业展开讨论。）

### 9. 参考技术清单（题目给出，非强制）

- 核心框架：Java 17+、Spring Boot 3.x、Spring Cloud
- 架构模式：微服务思想、DDD 领域驱动设计
- 数据层：Spring Data JPA / MyBatis-Plus、MySQL / PostgreSQL、Flyway
- AI 集成：Spring AI、LangChain4j、或手动封装 HTTP Client（RestTemplate / WebClient）
- 工具库：Lombok、MapStruct、Hutool
- 测试：JUnit 5、Mockito、Spring Boot Test、Testcontainers

### 10. 附加材料

- 模型平台：阿里云百炼（DashScope），模型 `qwen-max`
- API 文档：`https://bailian.console.aliyun.com/cn-beijing/?tab=api#/api/?type=model&url=3016807`
- API Key：**由面试方单独提供（敏感凭证，勿写入代码 / 文档 / 仓库）**，本地运行时放入环境变量或 `.env`（并加入 `.gitignore`）。

## 第二部分：坑位分析

### A. 题目本身埋的"坑"（其实是隐藏考察点）

| # | 坑点 | 说明 |
| --- | --- | --- |
| A1 | **AI 输出 = 不可信输入** | 题目鼓励"让 AI 决定调用哪个业务方法"。若真把 LLM 返回的函数名/参数直接反射调用或拼 SQL，等于把系统的控制权交给了一个可被提示注入的模型。这是本题**最大的坑**。 |
| A2 | **"一致性 / 逻辑闭环"是重点词** | 见 B 组。题目特意点出"AI 响应与本地事务的一致性"，说明评审一定会看你怎么处理"AI 成功但本地失败 / 本地成功但 AI 超时"这类不一致。 |
| A3 | **"单体即可" vs 推荐 Spring Cloud** | 技术清单里出现了 Spring Cloud / 微服务，但明确说"单体演示即可"。这里诱导你**过度设计**（上 Nacos、Gateway、多模块拆分）。两天时间内上全家桶 = 主链路跑不通。 |
| A4 | **"配备 AI IDE，考察人与 AI 的结合能力"** | 反向的坑：作业里 AI 生成的代码如果你自己讲不清楚、改不动，下一轮面试现场会露怯。**成果必须是你自己能解释、能改的**。 |
| A5 | **API Key 明文给出** | 这是一个安全意识的测试点。把 Key 硬编码进 Java 文件或提交到仓库，是最典型的减分项。 |
| A6 | **"Function Calling 或直接业务处理"** | 措辞很松，容易让人以为二者等价。实际 Function Calling 的工程复杂度（工具注册、参数校验、二次调用）远高于"直接业务处理"，需要评估两天时间是否值得。 |

### B. 一致性与事务（题目明示的核心，也是 P0 级坑）

| # | 坑点 | 说明与建议 |
| --- | --- | --- |
| B1 | **在 `@Transactional` 里调用外部 AI 接口** | AI 走网络，慢/超时都会让事务**长时间持有数据库连接和行锁** → 连接池耗尽、锁等待、级联故障。**不要在事务内发外部请求**：AI 调用放在事务外，拿到结果后再开短事务写库。 |
| B2 | **AI 调用成功但本地事务回滚** | 例如 LLM 已生成结果、写库时校验失败回滚 → 状态不一致。需要明确"补偿 / 重试 / 落流水表"的策略。 |
| B3 | **本地成功但 AI 超时（其实 AI 已成功）** | 重试会产生**重复执行业务动作**（重复下单）。必须引入**幂等键（idempotency key）**。 |
| B4 | **重试非幂等操作** | "创建订单"这类写操作不能无脑重试。区分可重试（读/查询类）与不可重试（写类），或写操作带幂等键。 |
| B5 | **流式响应（SSE）持有长连接** | SSE 期间**不要开事务**、不要占用请求线程做阻塞循环。SSE 完整结束后再落库。 |

### C. AI 集成的健壮性

| # | 坑点 | 说明与建议 |
| --- | --- | --- |
| C1 | **LLM 返回非法 JSON** | 模型常把 JSON 包在 ```json 代码块里、带解释性前缀、字段缺失或类型错误。需要**容错解析**（提取代码块 / 宽松模式）+ 失败重试 + 兜底文案。 |
| C2 | **超时 / 重试 / 退避 / 熔断缺失** | 题目明确考"超时、异常、重试"。要区分：连接超时 vs 读超时；重试次数 + 指数退避 + 抖动；连续失败熔断。注意**重试放大风暴**。 |
| C3 | **非确定性导致测试不稳定** | 同样输入模型输出不同 → 测试不能依赖真实模型。用**接口抽象 + Mock/Fake**，单测不打真实 API（同时避免烧配额）。 |
| C4 | **配额 / 成本** | qwen-max 按 token 计费，流式长文本更贵；异常重试会成倍烧钱。演示时注意控制。 |
| C5 | **qwen-max 的接入细节** | DashScope 有**原生模式**（`tools`+`tool_choice`，流式需 `X-DashScope-SSE: enable` 头）和 **OpenAI 兼容模式**（`https://dashscope.aliyuncs.com/compatible-mode/v1`）两套，SSE 帧格式不同。**"流式 + Function Calling"同时用是已知的复杂点**，两天内要谨慎。另：题目给的文档链接是控制台页面，需登录。 |
| C6 | **先验证连通性** | Key 可能额度受限/未开通该模型/已失效。**第一天就先写一个最小连通性脚本**验证，别等到最后才发现调不通。 |

### D. 架构与工程（加分项反而容易踩坑）

| # | 坑点 | 说明与建议 |
| --- | --- | --- |
| D1 | **Spring Boot 3 = `jakarta.*`** | Boot 3 把 `javax.*` 全换成 `jakarta.*`。网上大量示例还是 `javax.persistence`，**直接抄会编译失败**。 |
| D2 | **API 文档别用 SpringFox** | SpringFox 不支持 Spring Boot 3，会启动报错。用 **springdoc-openapi**（`springdoc-openapi-starter-webmvc-ui`）。 |
| D3 | **Flyway 与 JPA `ddl-auto` 冲突** | 用了 Flyway 就该设 `ddl-auto=validate`（或 none），否则 `update` 与迁移脚本打架，schema 混乱。 |
| D4 | **WebFlux + JPA 阻塞冲突** | 若为了 SSE 用 WebFlux，又用阻塞的 JPA，会阻塞事件循环线程。需 `boundedElastic` 调度；或干脆用 Spring MVC 的 `SseEmitter` 更省事。 |
| D5 | **Docker 一键运行的启动顺序** | app 容器会在 MySQL 就绪前启动。需要 `healthcheck` + `depends_on: condition: service_healthy`，或重试连接。 |
| D6 | **Testcontainers 依赖本机 Docker** | 加分项里的 Testcontainers 需要 Docker 环境；无 Docker 时测试会失败/跳过，别把主流程测试绑死在它上面。 |
| D7 | **Lombok + MapStruct 处理器顺序** | 两者共存需要 `lombok-mapstruct-binding`，否则生成的 Mapper 找不到 getter/setter。 |
| D8 | **演示用 H2 vs 生产 MySQL** | H2 与 MySQL 在方言、JSON 类型、`ON DUPLICATE KEY` 等语法上有差异。要么直接 Docker 起 MySQL，要么注意方言配置。 |
| D9 | **AI 适配层要真解耦** | 加分项要求"AI 适配层与业务层解耦"。应定义 `AiClient` 接口（端口），业务层只依赖接口；HTTP 实现、Mock 实现都是适配器。评审一眼就能看出是否解耦。 |
| D10 | **参数校验要覆盖 AI 来源的数据** | 别只校验前端入参。AI 生成/回填的 DTO 同样要过 `@Valid`，并且**业务规则和权限必须在服务端再校验一遍**。 |

### E. 安全（容易失分，且和 A1/A5 呼应）

| # | 坑点 | 说明与建议 |
| --- | --- | --- |
| E1 | **AI 驱动的越权查询（IDOR）** | "让 AI 决定查什么"时，若查询不按登录用户隔离，模型可被诱导去查他人数据。**数据权限在服务端按当前用户强制收窄**。 |
| E2 | **禁止 AI 直接触达 SQL / 反射** | 工具表用**白名单注册**（枚举安全的业务动作），参数强类型 + 校验；**绝不**让模型输出 SQL、类名或方法名后直接执行。 |
| E3 | **危险操作需二次确认** | 删除、退款、改价等不可逆动作，模型只能"建议"，必须人工确认或直接禁止。 |
| E4 | **日志泄露敏感信息** | 记录 prompt / response 时可能带入 PII、内部字段甚至凭证。脱敏后再打日志，**别把 Key 打进日志**。 |
| E5 | **凭证管理** | Key 只放环境变量 / `.env`（`.gitignore`），文档与代码里用占位符；本地 `.env` 不要提交。 |

## 第三部分：建议的最小可行设计（规避上述坑）

分层（体现解耦，别上微服务全家桶）：

```
api/          REST 接口 + 全局异常处理 + 参数校验
service/      业务逻辑 + 事务边界（只在这里开事务）
domain/       领域模型 / 实体 / 仓储接口（端口）
adapter/ai/   AI 适配层：AiClient 接口 + QwenHttpClient 实现 + MockAiClient
adapter/persist/  JPA 仓储实现
dto/ + mapper/    出入参对象 + MapStruct 映射
```

关键做法：

1. **AI 调用与事务分离**：`service` 先调 `AiClient`（无事务），拿到结果后再进 `@Transactional` 写库。
2. **工具白名单**：`ToolRegistry` 里注册允许的动作（如 `createOrder` / `queryOrder` / `updateStatus`），模型只能返回白名单内的工具名 + 结构化参数；参数经 `@Valid` 校验后由服务端执行业务方法（不反射、不拼 SQL）。
3. **幂等**：写操作带幂等键，重试与 AI 重复调用都去重。
4. **健壮调用**：`AiClient` 内实现 超时 + 有限重试 + 指数退避 + 失败兜底；对外统一抛业务可识别的异常。
5. **SSE**：用 Spring MVC `SseEmitter`（或 WebFlux + boundedElastic）；流结束再落库，全程不持有事务。
6. **工程化**：`@RestControllerAdvice` 统一异常、`springdoc-openapi` 文档、请求日志脱敏、Flyway 管 schema（`ddl-auto=validate`）。
7. **Docker**：多阶段构建 + 非 root 用户 + `MaxRAMPercentage`；MySQL 用 `healthcheck` + `depends_on` 保证就绪。
8. **先跑通的最小闭环**：`/api/orders/assistant` → AI 识别意图 → 白名单工具执行 → 写库 → 返回；**先保证这条链路通，再叠加分项**。
