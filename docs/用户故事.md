# Order Assistant 用户故事

> 本文档从**使用者视角**梳理本服务**已提供的**能力，以及**使用者会需要、但尚未实现**的能力，用统一的用户故事格式（角色 / 诉求 / 价值 / 验收标准）描述。它同时是下一步开发的 **backlog**。
> 已实现的故事标注它落到哪个接口、哪条架构决策（ADR），以便对照代码与设计文档核验；**未贴 `Status:` 的故事即表示已实现**。贴了 `Status:` 的是 backlog 或范围外条目，`ready-for-agent`（验收已定到可直接开工）/ `ready-for-human`（还差产品语义或表结构）/ `wontfix`（有意不做，见附录 D）三种取值与 [agents/triage-labels.md](agents/triage-labels.md) 对齐。
> 领域词汇以 [CONTEXT.md](../CONTEXT.md) 为准；架构决策见 [docs/adr/](adr/)；接口全貌见 [README.md](../README.md)。

## 0. 一句话定位

客户用自然语言让 AI 助手**查询**自己的订单，**并在确认后**才真正创建订单、或流转它的状态（`COMPLETED` / `CANCELLED`）。

核心主张：**AI 提议，人确认，服务端校验，价格由服务端决定。**

## 1. 角色

| 角色 | 说明 | 关注点 |
|---|---|---|
| **客户（Customer）** | 服务的主要使用者，拥有订单与对话；由**登录会话**标识（`POST /api/auth/login`，customerId + PIN） | 用最省事的方式查单、下单、改单，且不担心助手"自作主张"地改数据 |
| **助手（AI Assistant）** | 系统内的模型侧，通过 `AiAssistantPort` 接入；只能提议白名单内的结构化工具调用 | 理解意图、返回结构化参数，绝不直接触碰数据库或价格 |
| **开发者 / 运维** | 部署、演示、排障的人 | 无 Key 也能演示、可审计、容器化、文档齐全 |

> 越权是贯穿全程的约束：**任何查询都按登录会话的客户收窄**，他人的数据与本人的数据在接口层不可区分（防 IDOR）。
>
> **这张角色表是完整的，不是省略。** 没有客服、没有运营控制台、没有第二种角色，也没有服务间调用方——四条"不做"共用一个根因，记在 [ADR-0017](adr/0017-single-role-customer-self-service.md)，逐条列在文末的附录 D。

## E1 确认闭环：AI 提议，人确认

> 本史诗是整个服务的立足点。**一切变更类操作永不自动执行**——模型只能产出一张待确认卡片（`PendingAction`），由发起它的客户确认后才在事务里执行（[ADR-0001](adr/0001-pending-action-confirmation.md)）。
> `AssistantService` 在结构上就**没有能力**运行变更类 handler：唯一能跑到变更 handler 的入口是 `ActionConfirmationService`。

### US-1.1 发起一段新对话

- **作为** 客户，**我希望** 一键开始一段新对话，**以便** 从零向助手提问，不被上一段对话的上下文干扰。
- **验收标准**
  - `POST /api/assistant/conversations` 返回 201 与新建的会话（含 id、标题、最后消息时间）。
  - 不带 `conversationId` 直接 `POST /api/assistant/chat` 也等价于开新对话，并在响应里回带新会话 id，供下一次续用。
  - 新会话的标题为空，界面上显示为「新对话」。

### US-1.2 用自然语言查询我的订单（只读）

- **作为** 客户，**我希望** 说一句「我有哪些订单」就让助手查到我的订单列表，**以便** 不用记住接口就能看单。
- **验收标准**
  - 助手提议只读工具 `queryMyOrders`，服务端**立即执行**（只读工具不走确认）。
  - 结果**只含当前会话客户名下的订单**，且排除其他客户（与 US-6.1 同一条约束）。
  - 回复里**不出现原始 JSON**：结果由服务端渲染成中文人话并入助手消息——一句引导（「你名下有 N 张订单，最近一张是 `ORD-…`：」，超过一页时改成「你名下共 N 张订单，以下只列出最近 K 张」）、每单一个块（订单号 · 下单时间 · 中文状态 · `¥` 合计，下面每行一条明细），订单号与 sku 用行内代码保持等宽可复制（[ADR-0015](adr/0015-render-readonly-results-server-side.md)）。
  - 渲染块自带引导句，所以**模型一个字没写的回合也读得通**；这份人话就是下一轮的记忆内容（US-2.1 不回退）。引导句**永远点名最近一张**：列表本就按下单时间倒序，服务端说得出这句话，不等模型想起来 `limit`（US-1.9）。
  - 没有订单时说的是「你名下还没有订单。」，不是 `[]`；整整一页时把「共 N 张 / 只列了 K 张」写在引导句里，不把一页当成全部历史。
  - 工具可以按模型给的 `limit` 只取最近几张（`1..Paging.MAX_SIZE`，缺省 20）；**越界或非整数的 `limit` 报 `VALIDATION_FAILED`，不钳制**——钳制是把顾客的错悄悄改成另一个答案（[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md)）。
  - 工具只返回订单号、下单时间、状态、金额与明细摘要，不返回内部 id；原始负载（含 `total`/`returned`）仍随 `executed` 出去，供审计与排障。

### US-1.3 查询单个订单详情

- **作为** 客户，**我希望** 按订单号让助手查某一张订单，**以便** 确认某一单的具体明细。
- **验收标准**
  - 助手提议只读工具 `getOrderByNumber`（`orderNumber` 必填），立即执行。
  - 呈现与 US-1.2 同一种可读形态（同一个订单块，只是没有那句列表引导），顾客不必换一种读法。
  - 订单不属于本人时按「不存在」处理（`NOT_FOUND`），不泄露他人订单存在与否。

### US-1.4 提议创建订单（只提议，不执行）

- **作为** 客户，**我希望** 说「帮我下单 3 个 WIDGET-01」后看到一张待确认的卡片，**以便** 在真正落单前核对商品与数量。
- **验收标准**
  - 助手提议变更工具 `createOrder`；服务端**不执行**，而是落一条 `PendingAction` 并生成卡片。
  - 卡片标题、摘要、字段**全部来自工具自身**（`ToolCard`），不是模型的话：`createOrder` 每行一对「商品 / 数量」，卡片上**不会**出现 `lines:[{...}]` 这种参数原文。
  - 卡片带：能力令牌 `token`、确认/拒绝入口、过期时间、当前状态（`PENDING`）。
  - 此刻**数据库里没有新订单**；订单只在确认后才出现（US-5.2 会再次钉死这一点）。

### US-1.5 确认执行变更

- **作为** 客户，**我希望** 点「授权执行」后订单真正落库，**以便** 完成我确认过的操作。
- **验收标准**
  - `POST /api/assistant/actions/{token}/confirm` 在**一个事务内**：行锁 → 校验未过期未处理 → 执行变更 handler → 状态置 `CONFIRMED`。
  - 金额由服务端从 `catalog_items` 解析（模型只给 sku 与数量），订单号由服务端生成。
  - 响应带 `replayed:false` 与工具产出的结果（如订单号）。
  - 确认路径**不含任何网络调用**，因此可以且应该在事务里（[ADR-0002](adr/0002-ai-calls-outside-transaction.md)）。

### US-1.6 拒绝提议

- **作为** 客户，**我希望** 点「拒绝」后什么都不发生，**以便** 安全地取消一个我不想做的操作。
- **验收标准**
  - `POST /api/assistant/actions/{token}/reject` 只把状态置 `REJECTED`，**不执行任何业务操作**，订单数据保持不变。
  - 卡片在界面/历史里显示「已拒绝」，不再提供确认入口。

### US-1.7 提议取消订单 / 变更订单状态

- **作为** 客户，**我希望** 让助手帮我取消订单或把订单改为完成，**以便** 用对话完成状态流转。
- **验收标准**
  - 助手提议 `cancelOrder` 或 `updateOrderStatus`（目标状态只允许 `COMPLETED` / `CANCELLED`，模型给出枚举外的值按 `VALIDATION_FAILED` 拒绝，不冒泡成 500）。
  - 与 US-1.4/1.5 完全同构：先出卡片，确认后才执行。
  - 状态流转受服务端状态机约束：`CREATED → COMPLETED / CANCELLED`，`COMPLETED`/`CANCELLED` 为终态；非法流转返回 `CONFLICT`。

### US-1.8 「刚刚那个订单」指的是哪一单

- **作为** 客户，**我希望** 确认下单后接着问「查看刚刚这个订单」，助手答的就是我刚确认的那一单，**以便** 用指代继续对话，而不是把全部订单再倒一遍。
- **验收标准**
  - 那一单的订单号作为 **grounding 事实**注入系统提示词：来源是已确认动作的 `result_ref`（工具自己命名的那个号），按**客户 + 会话**过滤——别的客户、别的会话都拿不到（[ADR-0015](adr/0015-render-readonly-results-server-side.md)）。
  - 没有已确认动作的会话，提示词里**不出现**这一段（不拿空值糊弄模型）。
  - 实现方式不是加一个「查最近一单」的工具：理由同 [ADR-0006](adr/0006-ground-model-with-catalog.md)——模型可以想不起来调用。（[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md) 后来给 `queryMyOrders` 加了 `limit`，并把「模型想不起来」这一半交给**确定性兜底**而不是交给模型的自觉；本条的**按会话收窄**不变——它修的是指代，跨会话的「最近一单」归 US-1.9。）
  - 确认结果**不另写一条消息**进 transcript：卡片已经在渲染同一个结果，写了就是同一张单出现两遍。
  - 助手用**客户使用的语言**回答（提示词不再规定「用简洁英文回答」）；服务端渲染的那几行标签固定中文，这是[讲解手册 §15 诚实清单](面试作业-讲解手册.md)里主动报的一条已知缺口。

### US-1.9 「最近一次下单」答的就是最近那一单

- **作为** 客户，**我希望** 在一个新会话里问「查询最近一次下单」，助手答的是我名下**最近的那一张**，**以便** 不必自己从一页清单里挑，也不因为换了个会话就问不出答案。
- **验收标准**
  - 这一问的答案来自订单表本身：上一段会话确认的那一单，对本会话的 grounding 不可见——按会话收窄本来就是为「刚刚这个订单」设计的（[ADR-0015](adr/0015-render-readonly-results-server-side.md)）。
  - **三道闸，各管一件事**（[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md)）：引导句**保证**顾客至少看见「共 N 张 / 列了 K 张 / 最近一张是 `ORD-…`」，哪怕模型一个字都没写；`limit` 让模型**有能力**只取一单；被拒的参数**有界重问一次**负责纠错。
  - 模型给的 `limit` 越界或非整数：服务端**拒绝**（`VALIDATION_FAILED`），不钳制；把拒绝当成观察回喂给模型，**有界重问一次**。
  - 第二次仍然非法、或模型已经开过口（顾客已经看见半截话）：**不再问**，改用 schema 必需的那几个参数重跑，落在服务端默认范围上，并在回复最前面声明「`[检索参数有误，已按默认范围回答]`」——降级不是静悄悄的。
  - 回喂的那条观察**不进 transcript**：顾客没说过它，历史里也不该出现服务器的一句报错。
  - 一次模型调用仍然只留一行审计（US-7.1）：被丢弃的那次记 `ERROR`，重问的那次记它自己的结果。

## E2 会话与记忆

> 记忆的边界是 `Conversation`：一次模型调用只看到**单个会话**的最近 N 条（默认 N=20，`assistant.memory.window` 可配），不跨会话。端口 `AiAssistantPort` 本身不知道「会话」存在，它只收一串有序发言（[ADR-0003](adr/0003-ai-behind-own-port.md)）。

### US-2.1 多轮记忆

- **作为** 客户，**我希望** 助手记得这段对话里前面说过的话，**以便** 追问时不必重复背景。
- **验收标准**
  - 同一会话内，模型收到该会话最近 N 条消息（CUSTOMER → UserMessage，ASSISTANT → AssistantMessage，TOOL → 带前缀的 UserMessage）。
  - 「我刚才说要下单几个？」这类追问能回到正确数字；上一轮**工具结果**也在记忆里（可回答「我第一轮查到的总金额是多少」）——记忆里那份是服务端渲染的人话（[ADR-0015](adr/0015-render-readonly-results-server-side.md)），订单号与金额渲染后仍在场，所以这条能力不因「人话化」回退。

### US-2.2 会话隔离

- **作为** 客户，**我希望** 新开一段对话就彻底换一个上下文，**以便** 干净地开始新话题。
- **验收标准**
  - 「新对话」= 新建 `Conversation`；此后任何模型调用都**不再看到**旧会话的消息。
  - 记忆**不跨 Conversation**。

### US-2.3 查看历史会话与消息

- **作为** 客户，**我希望** 回到之前某段对话继续，或翻阅它的历史，**以便** 找回之前问过什么、得到过什么。
- **验收标准**
  - `GET /api/assistant/conversations` 列出我的会话；`GET .../{id}/messages` 返回完整历史（**当前不分页、无上限**，长会话整段拉回，见 US-2.7）。
  - 历史里每张卡片**解析为它当前的状态**（`PENDING`/`CONFIRMED`/`REJECTED`/`EXPIRED`），而不是当时的快照。
  - 访问他人的会话返回 **403**，不存在的会话返回 **404**（对外口径：他人会话与不存在不可区分）。

### US-2.4 会话标题自动生成

- **作为** 客户，**我希望** 侧栏用一句话概括每段对话，**以便** 一眼找到想找的那段。
- **验收标准**
  - 会话标题由该会话的**第一条客户消息**派生；创建后侧栏刷新反映新标题。

### US-2.5 断线后仍能找回这一轮

- **作为** 客户，**我希望** 就算网络中途断了，我发出的问题和助手的回答都不会丢，**以便** 下次打开能看到真实发生了什么。
- **验收标准**
  - 客户消息在**调用模型之前**就已提交；投递失败只是「没人听了」，回合照常跑完并持久化（[ADR-0009](adr/0009-stream-delivery-is-best-effort.md)）。
  - 前端在流断裂后**以服务端历史为准**做对账：恢复出「已回复 / 已落库但无回复 / 未发出 / 未知」四种结局，不乐观臆测。
  - 对账判定为「已落库但无回复」时，界面上给出**「没有收到回复」+ 一个「重试」按钮**（纯前端：检测会话最后一条是 CUSTOMER 发言即认定为有问无答；`sending` 中或该会话状态为 `RUNNING` 时不出现）。启动时对账把库里残留的 `RUNNING` Run 收敛为 `INTERRUPTED`（`RunReconciler`），状态列不说谎（[ADR-0011](adr/0011-run-is-the-unit-of-execution.md)）。
  - 重试**不续传半截内容**：它是一次全新的发送（没有重试端点，也不存在"恢复上一个 Run"）。它的语义边界见 US-2.6。

### US-2.6 重试不留下重复的提问

- **Status**: `ready-for-human`
- **作为** 客户，**我希望** 点「重试」之后，历史里只有我这一个问题、和它终于得到的那个回答，**以便** 回头翻这段对话时看不出这里曾经失败过一次，助手也不会以为我没听懂而重新解释。
- **验收标准**
  - 重试**复用**那条 CUSTOMER 消息，**不新增发言**：一段失败过的回合在 transcript 里呈现为「一问一答」，中间那次失败只存在于 Run 与审计里（US-7.1），不存在于对话内容里。
  - 重复的提问是**被污染的记忆**：模型在第三轮会把它读成"客户没听懂，所以又问了一遍"，于是开始换个说法解释同一件事——这个偏差没有任何地方要求过。
  - 重试**计为新的一次模型调用**（新 Run、新审计行、新花一次配额），这条不变；幂等键**不适用**——它本来就是"再说一遍"，不是"再发一遍同一个请求"（与 US-5.1 的边界写清楚）。
  - 连续失败时重试不叠加：第二次重试仍然复用同一条 CUSTOMER 消息，历史里永远只有一条。
- **预期落点**：前端 `AssistantView.retry()` 现在直接调 `send()`，所以要动的是发送路径——加一个"复用最后一条客户消息"的入参（或一个 `POST .../runs/{runId}/retry` 端点），让落库时不再 insert 一条 Message。定的是**产品语义**（复用还是新增），故 `ready-for-human`。

### US-2.7 长会话的历史分段取

- **Status**: `ready-for-human`
- **作为** 客户，**我希望** 一段用了几十轮的对话打开得和刚建的一样快，**以便** 找回三个月前那句"我当时说的第二个数量是多少"，而不是等它把全部历史搬完。
- **验收标准**
  - `GET .../{id}/messages` 支持分段读取，且**默认给的是最近一段**（客户打开时看到的是当下最该看的东西，不是第一条消息）。
  - 记忆窗口（US-2.1 的 N=20）不受影响：模型那侧本来就只看最近 N 条，这条只解决**给人看**的那份历史。
  - 分段边界要稳定：翻页不能因为中途来了新消息而重复或跳过某条（按 id 游标，不按偏移）。
  - 归档会话（US-9.5）读历史的口径与活跃会话一致，不因分段而少一段。
- **预期落点**：`ConversationService#history` → `ConversationRepositoryImpl#findAllMessages`（现在是一条 `eq(conversationId).orderByAsc(id)` 的全量 `selectList`，无 limit、无游标），`ConversationController` 加分段参数，前端 `api.ts` 的 history 调用跟上。**表结构不用动**，但"默认给最近一段"要和前端的整段替换逻辑一起定，故 `ready-for-human`。

## E3 流式回复（SSE）

### US-3.1 增量渲染助手回复

- **作为** 客户，**我希望** 助手的文字逐字出现，**以便** 不必干等整段生成完。
- **验收标准**
  - `GET /api/assistant/conversations/{id}/stream?message=...` 以 `token` 事件逐个吐字，最后一发 `done` 带与 JSON 接口**同构**的结果（含卡片）。
  - 会话靠 query 传参（`EventSource` 不能 POST）；消息流式只流**自然语言**，工具调用天然是原子的，卡片整张出现在 `done` 事件里。
  - 失败以 `error` 事件收尾。
  - 该端点**不做幂等**（流无法重放），需要重试请走带 `Idempotency-Key` 的 JSON 端点。

### US-3.2 流式池打满时立即得到反馈

- **作为** 客户，**我希望** 服务繁忙时马上被拒绝，**以便** 不把一个注定超时的连接挂着等。
- **验收标准**
  - 流式在**有界线程池**上运行；池满（并发占满且队列满）时在**发出任何事件之前**返回 **503 `SERVICE_BUSY`**。

### US-3.3 死连接不拖垮回合

- **作为** 客户，**我希望** 关掉页面或断网不会让助手白跑或让我的问题变成「有问无答」，**以便** 回来时回复还在。
- **验收标准**
  - 客户端消失只终止**投递**，不终止**回合**：模型跑完、结果落库、审计记成功。
  - 真正的失败仍走失败路径并落审计行。

## E4 订单与商品（传统业务接口）

### US-4.1 浏览我的订单列表

- **作为** 客户，**我希望** 看到自己名下订单的分页列表，**以便** 总览我的账目。
- **验收标准**
  - `GET /api/orders?page=&size=` 返回分页结果（默认 `page=1`、`size=20`，`size` 上界 100）。
  - 只出现当前客户名下的订单；每行显示订单号、状态、明细行数、金额。

### US-4.2 查看订单详情

- **作为** 客户，**我希望** 展开一张订单看到逐行明细与合计，**以便** 核对单价与数量。
- **验收标准**
  - `GET /api/orders/{orderNo}` 返回明细（sku、商品名、数量、单价、行金额）与合计。
  - 明细上的**商品名、单价、行金额都是下单瞬间的快照**（写在 `order_lines` 上），读取时**不回查目录**：目录后来改价、改名、下架，这张历史订单显示的仍是**当初成交的那个价**。「价格由服务端决定」的另一半是**服务端对历史负责**（[CONTEXT.md 的 CatalogItem 词条](../CONTEXT.md)）。
  - 对外报的合计由这些行快照**重算**得出（`OrderLine.lineAmount()` 求和），**不是**读 `orders.total_amount` 那一列。那一列在创建时写入、此后从不被读回（`OrderPersistenceMapper#toDomain` 建聚合时根本不带它）——所以两者只有在"写入后没人改过明细"时才相等，而**唯一可信的是重算那一个**。这条冗余当前无害，但它是一处没人守着的分叉，应进附录 C 的诚实清单。
  - 归属校验：非本人订单返回 `FORBIDDEN` / `NOT_FOUND`（防越权）。

### US-4.3 直接下单（不经助手）

- **作为** 客户，**我希望** 直接调 REST 接口下单，**以便** 在不用助手的场景也能建单。
- **验收标准**
  - `POST /api/orders` 返回 201 与订单；价格同样由服务端从目录解析。
  - 支持 `Idempotency-Key` 请求头（见 US-5.1）。

### US-4.4 浏览商品与单价

- **作为** 客户 / 演示者，**我希望** 看到可下单商品及其单价，**以便** 知道有哪些 sku、多少钱，也说明「价格只在这里定义」。
- **验收标准**
  - `GET /api/catalog/items` 返回全部**上架**商品（sku、名称、单价）；不分页，目录只有一个上架位 `active`（**没有库存、没有软删除**）。种子数据是迁移里硬编码的 5 行。
  - 下单时未知或已下架 sku 返回 `VALIDATION_FAILED`（HTTP 400）。
  - **助手那一路也要看得见这件事**：模型提议了一个已下架或不存在的 sku，卡片照常生成，但那一行的单价与合计渲染为「—」（价格由服务端解析，解析不出来就没有数字可写），确认时按 `VALIDATION_FAILED` 拒绝——**卡片能生成不等于卡片能执行**，这条边界此前没写。

### US-4.5 按条件查我的订单，并给我一个汇总

- **Status**: `ready-for-human`
- **作为** 客户，**我希望** 问「我还没取消的那几张」「上个月下单的，一共多少钱」，助手按条件答，**以便** 不用自己在一页清单里挑，也不用拿计算器加。
- **验收标准**
  - 只读工具支持**按状态与时间区间收窄**（`status` 走 `OrderStatus` 枚举、非法值按 US-1.9 那套拒绝并回喂，不钳制），不再只有"最近 N 张"这一种切法。
  - 结果带**汇总**：命中多少张、合计多少金额，由服务端算并渲染成人话（US-1.2 的 `ToolReport` 同一路子），模型不参与加总。
  - 超过一页时**给一条出路**：要么点名还有多少张没列出并可继续取，要么把 `GET /api/orders` 的分页能力接进来——不能只声明「只列出最近 K 张」就把客户堵在门里。
  - 条件收窄与防越权同向：条件只在这位客户名下的订单里筛（US-6.1），任何条件都换不来别人的订单。
- **预期落点**：`OrderToolDefinitions.queryMyOrders` 的 schema 与 handler、`OrderRepository` 的查询条件、`ToolReport` 的引导句。要新加一个查询条件而 `limit` 已经在那儿了——**先把"limit 与筛选同时出现时谁说了算"定下来**（当前没有答案），故 `ready-for-human`。

### US-4.6 问助手「有什么商品、多少钱」能答出来

- **Status**: `ready-for-agent`
- **作为** 客户，**我希望** 不必先去商品页就能问助手「你们那个小工具多少钱」，**以便** 下单这条对话路径从头到尾不用换界面。
- **验收标准**
  - 这一问**有确定答案**：目录的 sku / 名称 / 单价在每次调用前已由 grounding 注入提示词（US-6.3、[ADR-0006](adr/0006-ground-model-with-catalog.md)），所以它不是"看模型心情"，而是事实每次都在场。
  - 报价必须与 `/api/catalog/items` 一致，**且价格不来自模型的复述**：模型可以给数字，但落库金额永远由服务端解析（US-1.5、US-6.3）——答错价与报错价是两件事，这条只治前者。
  - 明确**没有** `listCatalog` 只读工具，且这是定夺而非缺口：理由同 ADR-0006（模型可以想不起来调用），外加工具数量是模型每次都要读的说明书。
  - 已下架的商品不出现在答案里（grounding 用的就是上架集），但客户拿着旧 sku 来下单时，走 US-4.4 那条拒绝路径。
- **预期落点**：`AssistantGroundingProvider`（已有，注入的是上架集）+ 提示词里一句「商品与单价以下由服务端给出，照此回答，不要臆造」。基本是措辞层与已有事实的确认，故 `ready-for-agent`。

## E5 一致性与可靠性

> 这一组直接回应题目「AI 响应与本地事务的一致性」。两条幂等路径各司其职（[ADR-0007](adr/0007-two-idempotency-paths.md)）：
> 客户端重试 → `idempotency_records`；重复点确认 → `pending_actions` 行锁 + 状态机。

### US-5.1 客户端重试不重复执行

- **作为** 客户 / 调用方，**我希望** 同一个请求重试不会重复建单或重复计费模型，**以便** 安全地应对超时后的重发。
- **验收标准**
  - 带 `Idempotency-Key` 的请求命中 `COMPLETED` 时**重放存储的响应原文**（连模型调用都不会发生第二次）。
  - 命中 `IN_PROGRESS` 返回 **409**（拒绝并发重复）；键相同但请求体哈希不同返回 **409**（键被挪用）。
  - 省略该头 = 不做幂等保护，每次执行。
  - 已接入入口：`POST /api/orders`（`CREATE_ORDER`）、`POST /api/assistant/chat` 与 `.../{id}/messages`（`SEND_MESSAGE`）。
  - **确认/拒绝不用此头**——`token` 本身就是唯一标识。

### US-5.2 重复确认不重复执行

- **作为** 客户，**我希望** 手滑点两次确认也只落一单，**以便** 不用担心重复提交。
- **验收标准**
  - 第一次确认执行并在事务内把状态置 `CONFIRMED`；第二次确认拿到行锁时状态已是 `CONFIRMED`，走**重放**（`replayed:true`）而不是再执行。
  - 重复确认返回它当初产出的引用（订单号），不是第二次执行。
  - 与已确认相反的操作（先拒后确认，或反之）返回 `CONFLICT`。

### US-5.3 卡片过期即失效

- **作为** 客户，**我希望** 搁置太久的卡片不能被执行，**以便** 避免误触一张过时的授权。
- **验收标准**
  - 卡片带 TTL（默认 15 分钟，`assistant.action.ttl-minutes` 可配）；过期在**读取时**判断，即使清理任务没跑，过期卡片也执行不了。
  - 过期后确认/拒绝返回 **410 `ACTION_EXPIRED`**，且对应业务操作**未被创建**。
  - `PendingActionSweeper`（`@Scheduled`，默认 60s）把超时行批量刷成 `EXPIRED`，让状态列说真话。

### US-5.4 上游 AI 超时/异常可识别且有界重试

- **作为** 客户 / 运维，**我希望** 上游故障被如实归类，并且不会无限重试拖垮服务，**以便** 快速定位和恢复。
- **验收标准**
  - 上游失败返回 **502 `UPSTREAM_AI_ERROR`**（而不是被误报成 500「我们的 bug」）。
  - 超时归类为 `TIMEOUT`、其他失败为 `ERROR`。
  - 同步调用有显式超时（连接 5s / 读取 60s）；重试收敛为 **3 次 / 1s / ×2 / 上限 8s**（把 Spring AI 默认的 10 次、上限 3 分钟收窄）。
  - 流式**首字节之前**失败整条重放（同款策略），**首字节之后不再重试**——重放会把已吐出的字再吐一遍。
  - AI 调用**绝不进数据库事务**（[ADR-0002](adr/0002-ai-calls-outside-transaction.md)）：模型可能跑好几秒，事务里不能握着连接等它。

### US-5.5 卡死的幂等键可重试

- **作为** 调用方，**我希望** 一个因故卡在 `IN_PROGRESS` 的幂等键不会永久占位，**以便** 用原键重试成功。
- **验收标准**
  - `IdempotencySweeper` 把过期仍 `IN_PROGRESS` 的键刷成 `FAILED`；`FAILED` 允许用原键重试（`reclaim` 回 `IN_PROGRESS`）。
  - 并发下「`FAILED` 重试只执行一次」由并发测试钉住。

### US-5.6 发得太快会被挡下来，并告诉我等多久

- **作为** 客户 / 运维，**我希望** 一个客户（或一群人）把模型配额冲爆时被立刻挡下来，**以便** 一个人的突发不会耗尽所有人的预算与工作线程。
- **验收标准**
  - **两道各自独立的闸**：每客户每分钟的发送数（`assistant.ai.rate-limit`，默认 **6**，60 秒滑动窗口）挡单个客户刷爆预算；全进程同时在飞的模型调用数（`assistant.ai.max-concurrent`，默认 **8**，公平 `Semaphore`）挡所有人一起冲垮上游。
  - 超出都回 **429 `RATE_LIMITED`**，并带 **`Retry-After`**：滑动窗口按剩余秒数回（至少 1s），permit 占满回 **2s**，上游自己回 429 时兜底 **5s**。
  - **不排队**——挡下来比排着快得多，也更诚实；忙时要排队的是同一会话的消息（US-9.2 的队列，超出 `429 QUEUE_FULL`），那是另一条闸。
  - **两个发送入口都拦**：JSON 那一路（`POST /api/assistant/chat`、`.../{id}/messages`）与流式那一路（`GET .../stream`）。流式**在进入 SSE 之前**就判，所以溢出是一条普通 JSON 429，不是一个错误帧——客户端不必先建一条注定失败的流。
  - 这条闸**按发送计数**，与 US-1.9 的有界重问同在一轮里时，一次发送最多占两个 permit 期（配额语义没变，成本上界翻倍，[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md) 已把这条代价写明）。
  - 与流式线程池的 503 `SERVICE_BUSY`（US-3.2）是三件不同的事，别混：那条是**池满**，这条是**配额**，US-9.2 那条是**同会话并发**。

## E6 安全、权限与定价

### US-6.0 用客户编号与 PIN 登录

- **作为** 客户，**我希望** 用客户编号和 PIN 登录，**以便** 之后的每个请求都自动是我的身份，而不是靠我自己声明。
- **验收标准**
  - `POST /api/auth/login`（`customerId` + PIN）建立会话；`GET /api/auth/me` 返回当前会话的客户；`POST /api/auth/logout` 登出。
  - 身份来自**会话**，不由请求头携带；未登录的请求一律 `401`，前端据此回到登录页。
  - 未知客户与错误 PIN 共用一条错误消息，登录端点不能被用来枚举客户。
  - 写操作要求 `X-XSRF-TOKEN` 头（cookie 会话下的 CSRF 防护）。
  - **身份由部署配置分配**：`customerId:PIN` 成对写在 `assistant.auth.pins` 里（**没有用户表，也没有注册**），改 PIN 意味着重新部署。客户是**业务键**，不是账号——这条是定夺，见 [ADR-0017](adr/0017-single-role-customer-self-service.md)。

### US-6.1 一切查询按客户收窄（防越权 / IDOR）

- **作为** 客户，**我希望** 我的订单与对话对别人不可见、不可改，**以便** 放心使用。
- **验收标准**
  - 所有业务接口都要求已登录会话，且**一切查询按会话客户收窄**。
  - 他人会话/订单按「不存在」或 `FORBIDDEN` 处理，调用方无法区分「不属于我」与「不存在」。
  - 演示价值：登出后用另一个客户登录再查，账目完全不同。

### US-6.2 只有卡片发起人能确认/拒绝

- **作为** 客户，**我希望** 只有我本人能确认我发起的操作，**以便** 知道令牌也不算数。
- **验收标准**
  - 用他人的 `token` 确认返回 **403**；不存在的 token 返回 **404**；已过期 **410**。
  - `token` 绑定发起客户，知道 token 不足以执行。

### US-6.3 AI 只能调白名单工具，价格由服务端决定

- **作为** 系统，**我需要** 把模型当作**不可信输入**，**以便** 提示注入或模型幻觉不能触碰数据库或价格。
- **验收标准**
  - 模型只能返回白名单内的工具名 + 结构化参数；未注册工具直接拒绝（`UPSTREAM_AI_ERROR`）。
  - 工具参数**只能**给 sku、数量与只读检索参数（`queryMyOrders` 的 `limit`）——**永远不能**给价格、客户 id 或枚举外的状态。检索参数同样按不可信输入对待：越界就拒绝并回喂，不钳制（US-1.9，[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md)）。
  - 金额一律由服务端从 `catalog_items` 解析；调用模型前由服务端把**模型不得臆造的事实**注入提示词（**grounding**）：当前 sku 与单价（避免臆造 sku，[ADR-0006](adr/0006-ground-model-with-catalog.md)）+ **本会话最近一次已确认的订单号**（让「查看刚刚这个订单」有确定答案，按客户 + 会话过滤，[ADR-0015](adr/0015-render-readonly-results-server-side.md)）。
  - 业务规则与权限在服务端**再校验一遍**，不信任 AI 生成的数据。

### US-6.4 登录会话有明确有效期

- **Status**: `ready-for-human`
- **作为** 客户，**我希望** 这套系统对"我还登录着"有一句话说得出口的期限，**以便** 我把电脑忘在咖啡馆时，下一个人打不开我的账目，也不用我先想起来登出。
- **验收标准**
  - 会话有**显式**的空闲超时与绝对上限，且**写在配置里**（今天两处都没有：既无 `server.servlet.session.timeout`，也无 cookie `Max-Age`，寿命实际是容器默认值——等于没人定过这件事）。
  - 过期后任何请求回 **401**，前端据此回到登录页（这条路径已有，US-6.0），**不要求客户端额外处理新错误码**。
  - 过期**不丢正在编辑的内容**：输入框里没发出去的那句话在重新登录后还在——「自动回到登录页」和"清空我写了一半的东西"是两件事，别让一件毁掉另一件。
  - 过期**不影响已落库的一切**：会话、历史、待确认卡片各按自己的规则活着（卡片过期见 US-5.3，它与会话过期是两条独立的时间线）。
  - 演示口径要能当场说清：默认期限取多少、为什么（演示要在几十分钟里不被踢，真实使用要短得多）。
- **预期落点**：`application.yml` 的 session/cookie 配置 + `SecurityConfig`，前端 `api.ts` 收到 401 时先把草稿暂存。**"期限取多少"是产品决断**（不是配置细节），故 `ready-for-human`。

## E7 审计与可观测

### US-7.1 每次模型调用留痕

- **作为** 运维 / 评审，**我希望** 每次模型调用都有一行审计，**以便** 事后核对成本、耗时与故障。
- **验收标准**
  - 成功走 `AssistantService.complete`，失败与超时走 `recordFailure`（同步与流式两条路径都覆盖）；失败行带 model、latency 与 `ERROR`/`TIMEOUT`。
  - **一次模型调用只留一行**。参数被拒后的有界重问（US-1.9）里，被丢弃的那次记 `ERROR`、重问的那次记它自己的结果，于是一轮顾客发送最多两行——每行都对应一次真实发生、真实计费的调用（[ADR-0016](adr/0016-refuse-illegal-arguments-and-re-ask-once.md)）。
  - 审计是**旁路**：写不进去只记一条 warn，**绝不影响**本轮回复。

### US-7.2 查看某会话的调用审计

- **作为** 客户，**我希望** 看到这段对话背后的模型调用记录，**以便** 了解每次调用花了多少、耗时多久、结果如何。
- **验收标准**
  - `GET /api/assistant/conversations/{id}/invocations` 返回该会话的调用（model、耗时、结果、时间）。
  - 归属校验同历史：他人会话 **403**。

## E8 工程化与交付

### US-8.1 没有 Key 也能完整演示

- **作为** 演示者，**我希望** 在没有 API Key 的环境下也能走通整条闭环，**以便** 任何机器上都能演示。
- **验收标准**
  - `SPRING_PROFILES_ACTIVE=mysql,offline` 激活 `MockAiAdapter`（同时关掉真实适配器），无需 Key。
  - 桩是关键词驱动的：说「我有哪些订单」提议 `queryMyOrders`，说「帮我下单 3 个 GIZMO-03」提议 `createOrder`，「提议 → 确认 → 落单」照样走得通。
  - 集成测试复用同一个桩，行为与测试所见一致。

### US-8.2 一键容器化运行

- **作为** 运维，**我希望** 用 Docker 一键起服务，**以便** 不依赖本地环境。
- **验收标准**
  - `docker compose up --build` 起 `mysql` + `app`；MySQL 带 `healthcheck`，`app` 等它 `service_healthy` 后才启动，避免 Flyway 与首次初始化抢跑。
  - 该流程已在本机实跑验证：镜像构建 → MySQL 初始化 → Flyway 建表 → `/actuator/health=UP` → 业务全通。

### US-8.3 可读的 API 文档

- **作为** 调用方，**我希望** 有在线 API 文档，**以便** 自助接入。
- **验收标准**：`GET /swagger-ui.html` 提供 OpenAPI 文档（springdoc-openapi）。

### US-8.4 统一响应体与错误码

- **作为** 调用方，**我希望** 所有接口用统一的成功/失败结构与稳定错误码，**以便** 一致地处理响应。
- **验收标准**
  - 统一响应体（`ApiResponse`）+ 全局异常处理（`GlobalExceptionHandler`）。
  - 稳定错误码：`VALIDATION_FAILED` / `NOT_FOUND` / `FORBIDDEN` / `CONFLICT` / `ACTION_EXPIRED` / `SERVICE_BUSY` / `UPSTREAM_AI_ERROR` / `RATE_LIMITED` / `QUEUE_FULL`。
  - 其中带重试提示的两个：**`RATE_LIMITED`（429）附 `Retry-After` 头**（US-5.6），`QUEUE_FULL`（429）表示同一会话队列已满（US-9.2）；`SERVICE_BUSY` 是 **503** 不是 429（流式线程池满，US-3.2）。
  - 入参校验覆盖**前端入参**与 **AI 来源的数据**。

### US-8.5 排障时能顺着一次请求找到全部日志

- **Status**: `ready-for-agent`
- **作为** 运维 / 评审，**我希望** 一次客户发送的所有日志行共享同一个标识，**以便** 出了故障能回答「这一轮到底调了几次模型、卡在哪一步」，而不是在并发日志里靠时间戳猜。
- **验收标准**
  - 每个请求带一个**关联标识**（`traceId` / `requestId` 之一），从入口生成、随 MDC 走，**跨线程不丢**——本服务的执行路径大量跨线程（流式在有界池上跑、Run 在调度里收敛、AI 调用绝不进事务），ThreadLocal 在这里天然会断，这是这条故事唯一真正的技术内容。
  - 日志里至少能同时看到：`customerId`、`conversationId`、`runId`、关联标识。有了这四个数，US-7.1 的审计行与日志行才对得上。
  - **只记标识，不记内容**：客户原文、模型原文、PIN 与 API Key 一律不进日志（[设计定稿 §8](面试作业-设计定稿.md) 的"日志脱敏"在代码里目前只有注释，没有实现兜住）。
  - 现状要说清楚：全服务只有 `logging.level…=DEBUG` 一行配置与散落的 `@Slf4j` 自由文本，**没有 MDC、没有关联标识、没有 logback 配置文件**——题目加分项「日志记录」目前兑现的是最薄的一层。
- **预期落点**：一个 servlet filter（生成/透传关联标识并写入 MDC）+ `AsyncConfig` 的装饰器把 MDC 带进有界池 + 一份 `logback-spring.xml` 把 pattern 定下来。不动表结构、语义无歧义，故 `ready-for-agent`。

## E9 会话管理（P1 延伸）

> 落地细节见 [会话管理-设计定稿](会话管理-设计定稿.md) 与 ADR-0011～0014。这些能力**不改变** E1 的确认闭环。

### US-9.1 会话状态看得见，且是实时的

- **作为** 客户，**我希望** 侧栏显示每段会话「生成中 / 待确认 / 安静」，并在**别的**会话跑完时自动更新，**以便** 不用来回刷新就知道哪里需要我。
- **验收标准**
  - 列表每项带 `state`（`IDLE`/`RUNNING`/`WAITING_APPROVAL`，派生）与正在跑的 `runId`。
  - `GET /api/assistant/events`（每客户一条长活 SSE）首帧 `snapshot`、之后推 `state`/`queue` 增量，重连重发快照。
  - 该流不占用回合线程池；每客户连接数有上限（超出 503）。

### US-9.2 同一会话的消息不并发赛跑

- **作为** 客户，**我希望** 在一段会话正忙时继续说，**以便** 不必等它跑完再开口。
- **验收标准**
  - 同一会话至多一个 `RUNNING` Run；**流式**发送忙时入队（先补 `queued` 带可删 `itemId`，轮到补 `started`），队列上限 5、超出 `429 QUEUE_FULL`。
  - **同步**发送忙时直接 `409 CONFLICT`；排队项不落库，重启即失。

### US-9.3 我能停止一个正在跑的回合

- **作为** 客户，**我希望** 点「停止」真的停下助手，**以便** 不为一句话继续付钱。
- **验收标准**
  - `POST .../runs/{runId}/stop` 只对 `RUNNING` 有效且幂等；**真**取消上游流（流式一路）。
  - 已收到的半截文本作为一条**普通 ASSISTANT 消息**落库（不写 Message 状态），Run 收 `CANCELLED`，审计记 `CANCELLED`。
  - 断线**不**触发停止（守 ADR-0009）；「停止」与「删排队项」是两个动作。

### US-9.4 切走再切回，接着看它吐字

- **作为** 客户，**我希望** 回到一段正在跑的会话还能看到当前进度，**以便** 不盯着屏幕等它跑完。
- **验收标准**
  - `GET .../runs/{runId}/events` 首帧给当前累积文本快照，之后给 `token` 增量；支持多个订阅者。
  - 服务端不缓存逐 delta（只持有当前累积文本）；对已终态的 Run 订阅以 `closed` 明确收尾，不悬挂连接。

### US-9.5 归档而不删除

- **作为** 客户，**我希望** 把不再看的会话收起来、随时恢复，**以便** 列表清爽又不丢东西。
- **验收标准**
  - `POST .../archive` / `.../restore`；归档后默认列表不含它，`?includeArchived=true` 可见；**没有硬删除**。
  - 非静止（有 RUNNING Run 或未过期卡片）归档 → `409`。
  - 向已归档会话发消息 → 自动恢复为 `ACTIVE`；归档不改动任何 Message 与审计行。

## 附录 C：已知缺口（诚实清单）

- 退避为简版：阻塞靠框架属性，流式只在首字节前自建重放，**中途失败不重试**；两处都**无 jitter、无熔断**。
- 卡片一侧的文字仍是英文：`ToolCard` 的标题（"Create Order"）、字段标签（Item / Quantity / Unit price / Line total / Total）与摘要（"Place order: GADGET-02 × 2"）由工具定义决定，界面其余部分与助手人话是中文；订单账目列表的状态列同为英文枚举（`CREATED`/`CANCELLED`），与助手回复里的「已创建」是两种呈现。
- 真实网络超时 → 真实退避的端到端行为由单测逐分支钉住，但**没有假上游**做端到端断言。
- `MockAiAdapter` 是关键词驱动的桩，只用于无 Key 演示，不理解真实语义。
- 浏览器两层要分开说：`frontend/story-walk`（走查，含 US-1.9）是**活着的那一层**，只跑 Chromium、助手走 `offline` 桩；而 `frontend/e2e` 那 14 条自 2026-10-14 会话登录改造后**从未跟进**——`e2e/support/viewer.ts` 还在往 localStorage 写 `ordermgt.customerId`、请求还带 `X-Customer-Id`，于是每条都停在登录页之前，实测 14/14 失败。这次没有修它（改的是被测代码之外的东西），只把事实写在这里。
- 走查里那条 `probe2.spec.ts` 是调试留下的探针，依赖库里已有 ≥2 段会话，空库上会红；它不是用户故事。
- 前端两层测试（L5 / L6）**尚未接入 CI**（仓库暂无 CI 配置）。
- Compose 只起单实例应用；确认态并发去重靠数据库行锁，多实例同样成立，但未做压测。
- 「模型会不会真用 `limit`」没有评测可跑：US-1.9 的验收钉的是**桩**与**渲染器**，真实模型的问题集回归需要 CI 与一把 Key，仓库两者都没有（前端两层测试同样未接 CI，见上一条）。
- 回喂重问的**成效**没有断言，只有审计：`limit` 被真实模型用了几次、拒绝后第二次调用改对了几成，只能临时对 `ai_invocations.tool_calls_json` 手写 SQL 去查，没有面板也没有阈值。
- 只读检索只会按时间收窄：`queryMyOrders` 有 `limit`，没有状态/时间区间的筛选，所以「我还没取消的那几张」这一问仍然只能靠服务端列出最近 N 张、由顾客自己看。

## 附录 D：范围外（有意不做）

> **这一节和附录 C 是两种东西**：附录 C 是"我知道它缺、我能修、这次没修"；这一节是"我想清楚了，不做"。混在一起读，评审就分不清哪条是疏忽、哪条是判断。这一节不是故事，没有验收标准，每条按 `wontfix` 处理。

- **`wontfix` — 卡片上改完数量再确认。** 现状确认执行的是**存下来的那串参数**（`argumentsJson`），界面上卡片是一组只读的 label/value。放开编辑意味着确认的对象从"模型的提议"变成"客户最终签认的参数"——那是另一种产品，得先改掉 §0「AI 提议，人确认」这句主张，牵动比这条需求值钱得多。真正反复发生的是**过期**（15 分钟 TTL 且无提醒），不是改错数量。
- **`wontfix` — 改历史订单的行项目 / 取消后恢复。** 状态机只有 `CREATED → COMPLETED / CANCELLED` 两条边，后两者是终态。误取消的一单要"恢复"就得引入状态机的第三条边与它的审计，而这份作业的立场是**终态就是终态、要重来就下一张新单**。§0 已把"变更"收窄为"流转状态"，不再承诺更多。
- **`wontfix` — 库存与可用性。** `catalog_items` 只有 `active` 一个上架位，没有数量列，下单不扣减、不预留。这是**目录**不是**仓储**；把它当缺陷就会滑向"超卖怎么办"那一整片范围。
- **`wontfix` — 客服台、角色与权限模型、服务间认证、注册与 PIN 自助管理。** 四条共用一个根因：本产品只有"已登录的客户本人"这一个角色，身份来自部署配置里的 `customerId:PIN`，**没有用户表**。定夺与代价见 [ADR-0017](adr/0017-single-role-customer-self-service.md)。由此推出的诚实缺口：**没人替客户审那张待确认卡片**——他不在，卡片就到期作废（US-5.3）。
- **`wontfix` — 跨会话的"待我确认"收件箱。** US-9.1 已经把 `WAITING_APPROVAL` 按会话推给每条流，客户在哪个会话就该在哪张卡片上做决定；再做一个聚合视图是第二个"哪里需要我"的答案，而它和侧栏那个派生状态说的是同一件事。
- **`wontfix` — 硬删除会话与消息。** 见 [ADR-0013](adr/0013-archive-hides-does-not-delete.md)：归档只管可见性，审计要留痕，硬删是一条换不来任何东西的数据丢失路径。要合规删除得另开一条带审计的路。
- **`wontfix` — 移动端弱网与无障碍。** 现有前端是桌面单页；`Last-Event-ID` 断点续传被 ADR-0009 明确推迟到"移动端弱网成为真实高频场景"再说，那个场景还没到。这不代表界面已经无障碍达标——它也没测过。
- **`wontfix` — 客户对助手答复的反馈通道（赞/踩、报错）。** 有 `ai_invocations` 审计（US-7.1）记录**调用是否成功**，但"成功了却答得不对"没有任何地方能收。真实产品需要它，这次的范围是后端集成，故不做——**代价是这份文档里所有"助手答得对不对"的故事，验收只能靠人读**。
