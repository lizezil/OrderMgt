# 会话状态靠推送：每客户一条长活 SSE，快照 + 增量，绝不占用回合池

多会话并行时，用户看着 A 段，B 段的回合跑完了、冒出一张待确认卡片——侧栏的徽标要能变。今天前端没有任何跨会话的实时通道（无 store、无全局流、无轮询），最省事的做法是「只在导航/刷新时拉一次列表」，但那意味着侧栏的状态永远是过期的。

**决策：新增 `GET /api/assistant/events`，每客户一条长活 SSE。** 首帧推 `snapshot`（该客户全部会话的 `{id, title, status, state, lastMessageAt}`），此后推增量事件：`state`（某会话状态变化）、`queue`（队列变化）、`ping`（心跳保活）。客户端重连时服务端**重发一次完整 `snapshot`**、客户端整体替换，**不做 `Last-Event-ID`**——续传需要服务端按序号缓存事件，而 ADR-0009 已经否决了这类缓存。线上格式复用现有 `event:` / `data:` 帧，前端 `parseSseFrame` 原样复用。

**这条长连接绝不能跑在回合池上。** `assistantStreamExecutor` 是**有界** `ThreadPoolExecutor`（默认 `max-concurrent=20`、`AbortPolicy`），专跑「有头有尾的回合」；一条页面级长活连接占一个线程不放，几个标签页就能把池吃光、让真正的回合全部 503。所以状态流走**另一套机制**：进程内的 `ConversationEventBus`，按客户维护一份 `SseEmitter` 注册表，订阅/退订走 emitter 回调、**不长期占线程**，断线按现有 `clientGone` 同款套路清理，配心跳保活与每客户连接数上限。两个池的语义要分清：**回合池 = 有界、可拒绝、会忙；状态总线 = 长活、不拒绝、只清理。**

**「重订阅一个正在跑的 Run」用同一套思路。** `GET /{id}/runs/{runId}/events`：订阅首帧给**当前累积文本快照**，之后给 `token` 增量。这**不违反 ADR-0009**——ADR-0009 反对的是「按 delta 缓存 / 按消息批量 UPDATE」，而「当前累积文本」注册表本来就持有（对应 `SpringAiAdapter` 的 `StreamedTurn`），发一次快照是无状态的，不是续传缓存。

**前端加一个模块级单例 composable，不引状态库。** 状态从「`AssistantView` 里一堆 `ref`」扩散成了跨组件、跨会话的共享态（侧栏徽标、跨会话队列），但前端运行时依赖目前**只有 `vue` 一个**。用一个模块级单例 store（`useSessionStore()`）承载「会话列表 + 每会话运行态 + 队列 + 状态流订阅」即可，Vitest 测法不变、零新增依赖；`AssistantView` 降级为该 store 的一个视图。Pinia 记为升级路径，状态真的复杂起来再加。

**排除的选项。** 轮询（白白打 DB、延迟抖动，与项目「有界、诚实」的调性不合）；WebSocket（现有栈是 fetch-SSE，别引第二种实时协议）。

**代价，说明白：** 重连瞬间要多传一次全量快照（换来零服务端事件缓存，值）；`max-concurrent=20` 仍是**全局**上限，一个客户可以开满 20 个 Run 让其他人饿死——**每客户并发配额**记入已知缺口；状态总线是**进程内**的，多实例下不跨实例广播，同属已知缺口。
