# 重新发起铸一张新卡：旧行不复活、不重问模型、不执行变更

E1 到今天只有两个写入口：确认与拒绝。两者是**同一种动作的两个方向**——对同一行 `PendingAction` 做出裁决，共用一个状态机（[ADR-0001](0001-pending-action-confirmation.md)）：同一裁决重放报旧结果，反向裁决 409，死卡 410。US-1.12 引入第三个写入口 `POST /api/assistant/actions/{token}/reinitiate`，它和它们是两种动作：**不是裁决，是重新提议**。

**决策：重新发起 = 用卡片自己存下的事实铸一张新卡；旧卡、旧 token、历史一切照旧。**

- **旧行不复活。** 原 `PendingAction` 保持 `EXPIRED`，旧 token 继续返回 `ACTION_EXPIRED`；重发起是**一行新记录**：新 token、TTL 从头起算（US-5.3 的默认 15 分钟）。「过期」是发生过的事实，历史不改写——同 [ADR-0013](0013-archive-hides-does-not-delete.md) 的立场。
- **不重问模型。** 用卡片存下的 `toolName` + `argumentsJson`（模型当初的提议）原样重提。客户要的是「同一件事再一次」；重跑模型既有成本与延迟，又可能提出和刚才那张**不一样的东西**。
- **不执行任何变更。** 重发起只是一张新的等待授权卡；能跑到变更 handler 的仍然只有确认入口（E1 开篇的结构不变）。
- **准入只认「真的死了」**：`EXPIRED`，或清扫器没跑、读取时已过 deadline 的 `PENDING`（口径同 US-5.3）。仍活着或已终结（CONFIRMED / REJECTED）→ `CONFLICT`；归属校验与确认、拒绝共用同一个读法（US-6.2）。
- **不去重。** 连点两次得到两张各自有效的卡——与模型重复提议同构，确认哪张算哪张（各过 US-5.2 的重放口径）。入口只长在 `EXPIRED` 上；`REJECTED` 不给——拒绝是客户的意思表示，重来该由客户重新开口。
- **进历史像一次新提议**：新卡追加一条卡片消息，旧卡留在原处；状态照常推送（新卡让会话回到 `WAITING_APPROVAL`，[ADR-0014](0014-conversation-state-is-pushed.md)）。

**边界：重发起不是「恢复会话」。** 已归档的会话里重发起会得到一张新卡（卡片过期后才归档得掉，归档的清静闸只查那一刻），会话**不因此自动复出**——复出有它自己的显式入口（恢复，[ADR-0013](0013-archive-hides-does-not-delete.md)）。把重发起也当「意图复出」说得通，但那条口径归 ADR-0013，不在这条里顺手改；归档是可见性，不是冻结，卡在归档的会话里照样确认得掉。

考虑过的替代方案：

- **复活旧行**（续 `expiresAt`、复用 token）。放弃：一个 token 曾答过 `ACTION_EXPIRED`，改答案会让「过期 → 410」这一对不再确定；旧页面上那张盖过「已过期」戳的卡突然又能确认，比过期本身更难解释。
- **重问模型**（拿原消息重跑一轮）。放弃：见上——客户点名「一字不改」，重跑是另一种提议。
- **确认过期卡时自动重提议。** 放弃：那是给一个已被拒绝的动作悄悄续命；重提议必须是客户的明确动作。
- **按（会话，工具，参数）对场上的活卡去重。** 放弃：模型重复提议本来就允许；去重会引入「点了按钮却冒出另一张」的隐形状态。

代价，说明白：`pending_actions` 多出重发起的行（每次一行，连点两次两行）；E1 的写入口从两个变三个，权限 / 状态机 / TTL 各自多一层测试面；卡片摘要**按今天的渲染器重算**（[ActionCardFactory](../../backend/src/main/java/com/example/ordermgt/assistant/application/ActionCardFactory.java) 不照抄存下的那句），工具改过措辞后同一会话里新旧两张卡可能说两种话——这是有意的：卡片是当次呈现的呈现，不是冻结的文本。
