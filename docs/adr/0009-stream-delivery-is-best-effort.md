# 流式的投递与回合解耦：断线只停止投递，不停止生成

SSE 是两个独立故障域叠在一起：**投递**（连接还在不在）和**回合**（模型跑完没有、落库没有）。旧实现把两者绑死——`emitter.send` 撞上断线抛异常，一路穿透 Reactor 的 `doOnNext` 把模型调用整个取消，回合走进失败分支。而客户消息在 `prepare` 里已经先入库了，于是每个中途关掉的标签页都在历史里留下一条**有问无答**；模型已经产出（已经计费）的内容被整体丢弃；审计还把"没人收"记成模型 `ERROR`。

**决策：投递是尽力而为，回合不是。** 连接断开（`send` 抛异常，或容器先通过 `onError`/`onTimeout` 报告）只翻转一个 `clientGone` 标志——从那一刻起不再往线上写任何事件，但模型照常跑完，`complete()` 照常把回复、卡片和 `OK` 审计落库。"没人听"是一行日志，不是一条失败审计。模型真正失败时仍走 `recordFailure`，`error` 事件照旧上线，行为与改造前完全一致。

**为什么不"断线即取消 + 落半截"？** 那需要给 Message 加状态列（streaming/complete）、按时间或字节批量 UPDATE、历史接口处理半截消息——写放大加上"回复停在半句话"的观感，换来的只是断线后那几个 token 的费用。而关掉页面再回来的客户，想看到的恰恰是完整回复。回答短（提示词要求 concise）、流有 2 分钟硬上界，继续跑的成本有界，不值这套复杂度。

**为什么不做 `Last-Event-ID` 断点续传？** 那要服务端按序号缓存 delta、客户端带 ID 重连、跳过已收到的部分，改动量大；而配合前端"断流后拉 `history` 对账 + 有界重试"，用户可见的丢失已经堵住（见 `AssistantView.reconcile`）。等移动端弱网成为真实高频场景再考虑，到时服务端缓存的接入点就是 `deliver`。

**前端契约随之改变：断流后不猜，问服务端。** 流断了既可能什么都没发生（请求没到、503 在 `prepare` 前），也可能客户消息已入库、回复还在路上（后端会继续写完）。所以拉 `history` 按事实裁决：回复到了→静默换上服务端真相；消息在但回复没等到→保留气泡、**不把草稿还回去**（服务端已有这条，还草稿等于诱导重复发送）；查无此消息→撤回气泡、草稿还给客户；历史都拉不到→保留本地状态并报错。

**代价，说明白：** 断线后仍会为没人听的 token 付费；工作线程最多占用到 120 秒超时（有界池 + `AbortPolicy` 已经限住总量）。这是买"回复永不因关页面而丢"的钱。
