# 幂等的两条路：通用幂等键用“插入占位”，确认操作用“行锁 + 状态机”

这里有两类重复，成因不同，因此用了两种机制，而不是硬凑成一套。

**一、客户端重试（发消息、直接建单）→ `idempotency_records`。** 调用方带 `Idempotency-Key`。占位靠 **INSERT 撞唯一键** `(customer_id, operation, idempotency_key)`，不做先查后写——并发重试不可能双方都插入成功，数据库唯一约束才是仲裁者。赢家跑动作，把响应体存进 `response_json`；后到的重试直接重放这份 JSON，模型调用和建单都不会发生第二次。**同一个键但 `request_hash` 不同 → 报 409**，因为这是键被挪用去干别的活，不是重试。选 `request_hash` 而不是只比键，是为了让"键被复用"这件事在系统里可见。

**二、重复点击确认按钮 → `pending_actions` 的行锁 + 状态机。** 确认天然有一个唯一的服务端标识——token，不需要客户端再给键。`SELECT ... FOR UPDATE` 锁住那一行，在同一事务里检查状态：并发的第二次确认会阻塞在锁上，等它拿到行时状态已经是 `CONFIRMED`，于是走重放分支而不是再执行一次。过期也在同一次读取时判断，所以哪怕清理任务没跑，过期卡片也执行不了。

**为什么通用幂等组件不是 `@Transactional`？** 因为它要保护的动作用可能包含 AI 调用，而 AI 调用绝不能待在数据库事务里（ADR-0002）。所以占位 INSERT、动作、标记 COMPLETED 是三个独立提交。代价要说明白：如果进程在"动作已提交"与"标记 COMPLETED"之间挂掉，这个键会停在 `IN_PROGRESS`，重试会被拒绝，直到记录过期。`IdempotencySweeper` 把过期仍停在 `IN_PROGRESS` 的记录刷成 `FAILED`，于是可以用原键重试——这是个有边界的缺口，不是没想到。

**重放返回的是"当时那份响应"，还是重新读一遍数据？** 选前者（存 `response_json`）。重放要么逐字节一致，要么不叫重放：重新读一遍会返回"现在"的状态，那样同一个请求两次调用可能得到不同答案。
