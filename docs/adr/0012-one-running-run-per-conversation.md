# 一个会话同时只有一个运行中的 Run：忙时入队，停止是显式意图

多会话并行的爽点在于「我在 A 段提问，不切回去也能在 B 段接着说」。这要求系统对「同一个会话又来一条消息」给出一致的答案，而不是让两次模型调用在同一段记忆上赛跑——今天没有会话级并发控制，两发同会话谁也不挡谁，记忆窗口会被交错写入。

**决策：同一 Conversation 至多一个 `RUNNING` Run。** 会话忙时，新消息进入**内存队列**（FIFO），轮到自己才被调度成一条普通的 Run 与普通的消息写入。队列有深度上限（取 5），超出返回**新增错误码 `QUEUE_FULL`（429 Too Many Requests）**——满了是容量问题，不是状态冲突，所以不是 409。队列项**不落库**，只活在运行态注册表里；代价是它们**随进程重启一起丢**，这与「排队没有 DB 行」是同一取舍，接受。

**只有流式入口排队。** `GET /{id}/stream` 忙时入队并在轮到自己时开始吐字；同步入口 `POST /{id}/messages` 在会话忙时直接 **409 `CONFLICT`**。理由：同步入口带 `Idempotency-Key`，是「原子、要么立刻执行要么拒绝」的路径，把长阻塞语义搅进幂等路径会让重试语义变得难以推理。

**「停止」是用户的显式意图，不是断线的副作用。** ADR-0009 已定：连接断开只停投递、回合照常跑完。因此停止必须是一个**独立的动作**——`POST /{id}/runs/{runId}/stop`，只对 `RUNNING` 有效。它**真正取消上游**（abort 到模型的流），因为一个不省钱的「停止」没人会点。被停止的 Run 把**已收到的半截文本作为一条普通的 `ASSISTANT` 消息落库**（不写 Message 状态，守 ADR-0009），状态置 `CANCELLED`，审计 `ai_invocations.outcome` 记一行 `CANCELLED`——该列是 `VARCHAR(16)` 且无 CHECK，**加这个值零迁移**。

**队列与停止是两个动作，别合并成一个按钮。** 停止作用于 `RUNNING` 的 Run；清空或删除一条**排队**消息是 `DELETE /{id}/queue/{itemId}` 这类独立操作。排队项必须暴露一个**内存态 id** 给前端（注册表生成、随状态事件带出），否则前端看得见却删不掉。队列不允许重排——FIFO 就够，重排是伪需求。

**Run 归属客户，不归属连接。** 同一客户开两个标签页，任一标签页都可以停对方发起的 Run（服务端的 Run 本来就独立于连接存在）；对已停的 Run 再停是**幂等**的，不报 500。两个标签页同时往同一会话发消息，由上面那条不变量天然串行成「一发一排队」。

**代价，说明白：** 不变量只在进程内保证（注册表）+ `(conversation_id, status)` 普通索引，**库层不强制**唯一 RUNNING——单实例成立，多实例会破，记入已知缺口；被拒绝的同步入口需要调用方自己重试（有 `Idempotency-Key` 兜底）；队列有上限，突发时用户会看到 429。
