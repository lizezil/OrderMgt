# 非法参数拒绝而不是钳制，回喂后有界重问一次

生产上的一段会话叫「查询最近一次下单」。模型那一轮做的事是：调用 `queryMyOrders`，参数 `{}`，**一个字都没写**。于是回复完全由服务端渲染（[ADR-0015](0015-render-readonly-results-server-side.md)），而渲染器能说的只有一句「你名下有 2 张订单：」加两张单——顾客问的是**一单**，拿到的是**一页**，而且没有一句话说清哪一张是最近的那一张。

这不是模型的错，是结构的：

- `queryMyOrders` 的 schema 是 `{"type":"object","properties":{}}`——模型**没有任何办法**只要求最近一单；它要么全查，要么自己数。
- [ADR-0015](0015-render-readonly-results-server-side.md) 注入的 grounding 是「**本会话**最近一次已确认的订单号」。跨会话问「最近一次下单」时那个事实按设计不可见（收窄本来就是为「刚刚这个订单」服务的），这一问唯一确定的答案来源是订单表本身。
- 提示词同时要求模型**不要复述工具返回的数据**——所以它留白是被鼓励的行为。留白的回合，答案只能由确定性代码组成。

**决策：三道闸，各管一件事——保证在渲染器，能力在 `limit`，纠错在有界重问。**

**一、渲染器定形（保证）。** 只读负载带上 `total` 与 `returned`，每条订单带上下单时间（时区与订单号自己的 `OrderNumber.ZONE` 同一个，否则「最近一单」的时间会和它自己的订单号差八小时），引导句**永远点名最近一张**：`你名下有 N 张订单，最近一张是 \`ORD-…\`：`，超过一页时改成 `你名下共 N 张订单，以下只列出最近 K 张`。列表本就按下单时间倒序，服务端说得出这句话，不等模型想起来 `limit`。实测那一轮光靠这一条就答对了。

**二、`limit`（能力）。** `queryMyOrders` 的 schema 加 `limit`：整数、`1..Paging.MAX_SIZE`、缺省 `Paging.DEFAULT_SIZE`，描述里写明「顾客只要最近一单时传 1」。**越界或非整数报 `VALIDATION_FAILED`，不钳制**——钳制是把顾客的错悄悄改成另一个答案（顾客要一单、`OrderService` 给他 20 单），而模型永远不知道自己被改过；报错了，它才有机会自己改对。

**三、有界重问（纠错）。** 只读 handler 抛出的 `VALIDATION_FAILED` 在 `AssistantService.complete` 里包成 `ToolArgumentsRejectedException`（带着是哪个工具、哪串参数——模型的提议从不落库，回喂时它已经看不见自己刚才提了什么），`executeTurn` 接住它：

- 只有当模型**一个字都没吐**（`turn.text().isBlank()`）时才重问。已经开口就不问：流式那边顾客已经看见半截话，第二段开场白比按错参数更糟。
- 回喂是一条 `Role.TOOL` 的临时记忆：机器话写给机器看——`{"tool":…,"arguments":…,"error":…,"executed":false}`。它**不进 transcript**（顾客没说过它，历史里也不该出现服务器的一句报错），怎么对待被拒的调用写在系统提示词里（[ADR-0010](0010-prompts-and-constants-live-in-one-place.md)）。
- **只重问一次。** 第二次仍然非法就不再问：改用「schema 声明必需的那几个参数」重跑（写错的通常正是多出来的那一个），落在服务端默认范围上，并在回复最前面声明 `[检索参数有误，已按默认范围回答]`——降级不是静悄悄的。
- 一次模型调用仍然只留一行审计：被丢弃的那次记 `ERROR`（顾客看不见它，所以它必须留下痕迹），重问那次记它自己的结果。

考虑过的替代方案：

- **钳制 `limit` 到合法区间。** 放弃，理由见上：把一个能被顾客看见的错误答案换成另一个没人声明的答案。
- **代码路由**（正则识别「最近/最新/刚刚」再决定调哪个工具、传什么参数）。放弃：那等于把自然语言查询降级成枚举意图，每加一种问法都要改代码；而它只修「最近一单」这一种，其它参数错误照样发生。
- **`required` 把 `limit` 变成必填 / `tool_choice` 强制调用。** 放弃：必填会让「我有哪些订单」也逼模型编一个数；强制调用**抢走的正是模型写正文的机会**，而实测的失败形态就是「只有调用、没有正文」——用确定性换僵硬，还换错了方向。
- **提示词里加一句「问最近一单就传 `limit: 1`」。** 放弃：[ADR-0015](0015-render-readonly-results-server-side.md) 已经否过同款——提示词拦不住「一个字都没写」，更拦不住「没想起来传」。
- **加一个 `queryLatestOrder` 工具。** 放弃：同 [ADR-0015](0015-render-readonly-results-server-side.md) 的否决理由（模型可以想不起来调用），另外工具数量是模型每次调用都要读的说明书，多一个就厚一页。
- **重试直到参数合法。** 放弃：每次重试都是一次真实计费加一段真实延迟。有界一次，加一道确定性兜底，最坏情况才有上界。

代价，说明白：**一轮顾客发送最多两次模型调用**——成本与延迟的上界翻倍（限流按发送计数、并发 permit 按调用持有，所以配额语义没变，但一次发送占两个 permit 期）；审计里一轮可能出现两行，按会话统计调用数会翻倍；`messages` 里看不到那次拒绝，排障要去 `ai_invocations.error`；兜底用的必需参数对「必需的键本身就是错的」情况仍然报失败而非降级（`getOrderByNumber` 少了订单号就没有安全答案可言，这是有意的）；重问只在留白时发生，因此它对「模型写了话但写错了」那一类失败**不生效**——那一类仍然只能靠渲染器；离线桩额外学了一条关键词（「最近/最新/刚刚」→ `limit:1`），它开始模仿一个它并不理解的意图。
