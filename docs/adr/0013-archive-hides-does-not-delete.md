# 归档是可见性，不是删除：只归档静止的会话

`conversations.status` 这一列从 V1 就在，设计定稿写的也是 `ACTIVE/ARCHIVED`，但它常年只被硬写成 `"ACTIVE"`——是个挖好没用的坑。现在把它填上，并明确它**只表达可见性**。

**决策：归档 = 置 `status='ARCHIVED'`。** 归档的会话从默认列表隐藏、**仍然可读**、可一键**恢复**为 `ACTIVE`，并且**不提供硬删除**。不硬删的理由有三重：审计要留痕、演示要可回溯、硬删是一条真实的数据丢失路径而它换不来任何东西。归档**不动任何消息与审计行**。该列是 `VARCHAR(16)` 且无 CHECK，**归档路径零迁移**。

**只允许归档「静止」的会话。** 若会话存在 `RUNNING` 的 Run，或存在未过期的 `PENDING` 卡片，归档返回 **409 `CONFLICT`**。这条把两个概念解耦得很干净：归档**只**管可见性，**不**兼任终止（要终止有 ADR-0012 的显式停止）。它带来一个漂亮的副产品——归档的会话**按构造**就不可能正在跑、也可能没有活卡片，于是「已归档会话里的卡片还能不能确认」这个问题**自动消失**（无卡可确认）。归档会话依旧可读、可恢复。

**向已归档会话发一条新消息 = 自动恢复为 `ACTIVE`。** 用户主动对它说话，意图已经明确，再要求先点一次「恢复」没有价值。这是唯一一条「写操作顺带改可见性」的规则，之所以安全，是因为它由用户的显式发言触发，不是后台的隐式动作。

**备选与否决。** 「归档时连带作废该会话的 `PENDING` 卡片」——被「只归档静止会话」吸收了：静止时根本没有待确认的卡片可作废，无需单独规则。「硬删（`DELETE`）」——否决，见上。「归档正在跑的会话并让它继续跑」——否决，那会让归档变成第二个半吊子终止开关，且用户看不见一段还在花钱的对话。

**代价，说明白：** 归档只增不减，列表会累积（对演示是卖点，对长期使用要靠归档分组来收敛）；没有硬删意味着数据永久保留——若将来要合规删除，需要另开一条带审计的删除路径，本次范围外。
