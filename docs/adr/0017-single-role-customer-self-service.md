# 只有客户自助这一个角色：不建用户表，不引入客服台、角色与服务间认证

[用户故事.md](../用户故事.md) 补进一批"使用者会需要"的故事后，一个反复出现的追问是：**谁来审这些待确认的动作？客服怎么替客户操作？另一个服务怎么调这些接口？** 它们共用同一个根因，所以在这里一次性定夺，而不是让每条故事各自解释一遍"为什么没有"。

现状是刻意的：**没有 `customers` 表**（[V1__init.sql](../../backend/src/main/resources/db/migration/V1__init.sql) 里 `customer_id` 是一个裸 `BIGINT`，无外键），客户身份来自部署配置的一对 `customerId:PIN`（`assistant.auth.pins`，[application.yml](../../backend/src/main/resources/application.yml)），**换 PIN 意味着重新部署**；认证只有一条 `ROLE_CUSTOMER`；`httpBasic` 与 `formLogin` 都关掉，身份**绝不从请求头取**（[CurrentCustomerResolver](../../backend/src/main/java/com/example/ordermgt/security/CurrentCustomerResolver.java) 没有 header 兜底）；唯一的免认证面是 `/actuator/health` 与 Swagger。

**决策：本产品只有一个角色——已登录的客户本人，且只有一种调用方——带会话 cookie 的浏览器。** 由此推出四条"不做"：

- **不做客服 / 运营控制台。** 一切查询按会话客户收窄（US-6.1），这条收窄正是防越权的全部内容；一个能看所有客户订单的角色会把它变成一条需要审计的权限系统，而它换不来这个作业要考察的任何东西。
- **不做角色与权限模型。** 没有 `roles` 列、没有 `ROLE_*` 分级、没有授权矩阵。[ADR-0013](0013-archive-hides-does-not-delete.md) 里"归档只管可见性、不兼任终止"是同一种克制：**一个概念只负责一件事**，第二个角色必然同时负责"能看什么"和"能改什么"。
- **不做服务间认证**（API key / Bearer / 签名）。题目写的是"供前端**或其他服务**调用"，但本服务的价值在 AI 集成闭环那一侧；机器调用需要的是一条与浏览器会话正交的凭证路径，而"身份不由请求头携带"（US-6.0）是它的前置主张——两者不能在同一份文档里都成立。
- **不做注册与 PIN 自助管理。** 客户是**业务键**，不是账号；有了注册页就需要邮箱、找回、锁定，那是另一个产品。

**备选与否决。** 「加一个 `admin` 角色，只做只读的全量查询」——否决：只读的全量已经越过了 US-6.1 那条"他人的数据与本人的数据在接口层不可区分"，而这条是文档里唯一被反复演示的主张（换一个客户登录，账目完全不同）。「给内部服务发一个静态 token」——否决：静态 token 一旦和会话 cookie 并存，"身份不来自请求头"就得降级成"多数时候不来自请求头"，而半条主张比没有主张更容易被误用。「留个 TODO 在故事里逐条注明」——否决：七个缺口共用一个根因，七次解释等于没解释。

**代价，说明白：** 演示与测试都得预先知道 `customerId:PIN`（配置里给的 `1001:1111` / `2002:2222`）；客户无法自助进入，注册流程仍是空白；任何真实多租户场景都要重做认证层；"谁审这些待确认卡片"这个真实运营问题在本产品里**没有答案**——只有发起它的那个客户本人能确认或拒绝（US-6.2），他不在，卡片就到期作废（US-5.3）。这几条都记在 [用户故事.md 附录 D](../用户故事.md) 里，不假装它们不是缺口。
