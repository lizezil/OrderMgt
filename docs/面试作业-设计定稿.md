## 3. 模块结构（按领域分包）

父 POM 只聚合 `backend/` 一个 Maven 模块；`frontend/` 是独立的 pnpm 项目，产物直接写进 `backend/src/main/resources/static`。**backend 单模块 + 领域分包**（不拆 Maven 子模块——两天内多模块构建只增加复杂度，不增加说服力）。

```
backend/src/main/java/com/example/ordermgt/
├── OrderAssistantApplication.java
├── shared/          统一响应体 ApiResponse、PageResult、ErrorCode、GlobalExceptionHandler(@RestControllerAdvice)、Paging
├── config/          MyBatisPlusConfig、OpenApiConfig、AsyncConfig(流式线程池)、AiHttpClientConfig(超时)
├── security/        SecurityConfig(会话 + CSRF)、AuthController(login/logout/me/csrf)、
│                    PinAuthenticationProvider、CurrentCustomerResolver/@CurrentCustomer
├── idempotency/     通用幂等组件：IdempotencyRecord、IdempotencyGuard、IdempotencySweeper
├── catalog/         商品目录（价格的唯一来源）：CatalogItem、CatalogController
├── order/           订单领域（核心域）：Order(聚合根)、OrderLine、OrderNumber、Money、OrderService
└── assistant/       助手领域
    ├── AiCallPolicy     模型调用的超时/重试常量（适配器与控制器共用）
    ├── domain/          无框架依赖：Conversation、Message、Run、PendingAction、ToolSpec、ToolCard、
    │                    ToolResult、AiAssistantPort、RunRepository 等端口
    ├── application/     AssistantService（编排）、ConversationService、ActionConfirmationService、
    │                    ActionCardFactory、ConversationRunQueue、RunService、RunRegistry、RunReconciler、
    │                    ConversationEventBus、CustomerRateLimiter、AiConcurrencyGuard
    ├── infrastructure/  Spring AI 适配器（ai/，prompt/ 集中提示词，tools/ 工具定义）、
    │                    MyBatis-Plus 持久化（persist/）、过期清理任务（schedule/）
    └── api/             控制器、DTO 与 MapStruct 的 ApiMapper
```

**依赖方向**：`api → application → domain`，`infrastructure → domain`（实现端口）。**domain 不含任何框架依赖。**
全仓有一处刻意的例外：`assistant/infrastructure/ai/tools/OrderToolDefinitions` 把只读工具接到 `order.application.OrderService` 上——工具定义本质是装配代码（哪个工具名对应哪个业务用例），这条 `infrastructure → application` 的边是单向的，`order` 侧不反向依赖 `assistant`，不构成环。

## 4. 领域模型与数据库（Flyway）

**聚合与关系**：`Order`(聚合根) ── 1..* `OrderLine`；`Conversation`(聚合根) ── 1..* `Message` ── 0..1 `PendingAction`；`Conversation` ── 1..* `Run`；`CatalogItem` 被 `OrderLine` 引用（按 sku）。

迁移脚本在 `backend/src/main/resources/db/migration/`：**V1** 建全部业务表与种子数据，**V2** 给 `orders` 加乐观锁列 `version`，**V3** 建 `runs`，**V4** 把幂等记录的结果存成文本。

### `catalog_items` —— 价格的唯一来源
`id` PK · `sku` UNIQUE · `name` · `unit_price DECIMAL(12,2)` · `active` · `created_at`
> 5 条种子数据（Flyway）。**AI 只选商品与数量，永不提供价格**——这是关键完整性规则。

### `orders` / `order_lines`
`orders`：`id` PK · `order_no` UNIQUE · `customer_id` · `status`(CREATED/COMPLETED/CANCELLED) · `total_amount DECIMAL(12,2)` · `version`(乐观锁) · `created_at` · `updated_at`；索引 `(customer_id, created_at DESC)`
`order_lines`：`id` PK · `order_id` FK · `sku` · `item_name` · `quantity INT CHECK>0` · `unit_price` · `line_amount`；索引 `(order_id)`
> 幂等**不在这张表上**——由 `idempotency_records` 承担，业务聚合保持干净。

### `conversations` / `messages` —— 记忆的边界与内容
`conversations`：`id` PK · `customer_id` · `title`（首条用户消息派生）· `status`(ACTIVE/ARCHIVED) · `created_at` · `updated_at` · `last_message_at`；索引 `(customer_id, last_message_at DESC)`
`messages`：`id` PK · `conversation_id` FK · `role`(CUSTOMER/ASSISTANT/TOOL) · `content VARCHAR(8000)` · `pending_action_id NULL` · `created_at`；索引 `(conversation_id, id)`
> 记忆 = 取该对话**最近 N 条**（默认 **N=20**，`assistant.memory.window` 可配）按时间正序回填；不跨 Conversation。
> `content` 落库前按 `Message.CONTENT_MAX`（8000）**截断**——超长直接 INSERT 会被数据库拒绝。只读工具的结果**由服务端渲染成人话**后内联进 ASSISTANT 消息（订单号 · 中文状态 · `¥` 合计 + 每行明细；模型自己的话在前），所以下一轮模型能"记得"上一轮查到的内容——内联的是渲染结果，不是原始 JSON（[ADR-0015](adr/0015-render-readonly-results-server-side.md)）。原始负载仍随响应的 `executed` 出去，审计与排障看得到机器真相。

### `pending_actions` —— 确认闭环的载体
`id` PK · `token` UNIQUE · `customer_id` · `conversation_id` · `source_message_id NULL` · `tool_name` · `arguments_json VARCHAR(4000)` · `summary` · `status`(PENDING/CONFIRMED/REJECTED/EXPIRED) · `expires_at` · `resolved_at NULL` · `result_ref NULL`；索引 `(customer_id, status, expires_at)`, UNIQUE`(token)`
> `token` 是 24 字节随机数的 hex（48 字符），是这张卡片的"能力凭证"；但光有 token 不够，确认请求里的会话还必须是**发起人本人**（`isOwnedBy`）。
> 这张表**不存响应体**，只存 `result_ref`（订单号）。重复确认返回"已确认过 + 结果引用"（`replayed:true`），确认的幂等保证是"不重复执行"，不是逐字节重放。
> `expires_at` 在**读取时**判断（confirm/reject 都查），即使清理任务没跑，过期卡片也执行不了；`PendingActionSweeper`（`@Scheduled`，默认 60s）另把超时行批量刷成 `EXPIRED`。`arguments_json` 超长由 `PendingAction.propose` **直接拒绝**（不截断——截断会造出一个"能执行但是错的"动作）。

### `ai_invocations` —— 审计与可观测
`id` PK · `conversation_id NULL` · `customer_id` · `model` · `prompt_tokens` · `completion_tokens` · `latency_ms` · `outcome`(OK/ERROR/TIMEOUT/CANCELLED) · `error NULL` · `tool_calls_json NULL` · `created_at`
> `messages` 给用户看，`ai_invocations` 给运维/审计看。**每次模型调用写一行**：成功由 `AssistantService.complete` 落库，失败与超时由 `recordFailure` 落库，停止记 `CANCELLED`。写入是旁路——写不进去只记一条 warn，不影响本轮回复。读取走 `GET /api/assistant/conversations/{id}/invocations`（归属校验同历史，他人会话 403）。

### `runs` —— 一次执行的记录
`id` PK · `conversation_id` FK · `status`(RUNNING + 终态 COMPLETED/FAILED/CANCELLED/INTERRUPTED) · `error VARCHAR(1000) NULL` · `started_at` · `ended_at NULL`；索引 `(conversation_id, status)`
> 详见 [会话管理-设计定稿.md](./会话管理-设计定稿.md) 与 [ADR-0011](./adr/0011-run-is-the-unit-of-execution.md)。

### `idempotency_records` —— 通用幂等
`id` PK · `customer_id` · `operation`(SEND_MESSAGE/CREATE_ORDER) · `idempotency_key` · `request_hash NULL` · `status`(IN_PROGRESS/COMPLETED/FAILED) · `result_ref NULL` · `response_json TEXT NULL` · `created_at` · `completed_at NULL` · `expires_at NULL`
UNIQUE `(customer_id, operation, idempotency_key)`；索引 `(expires_at)`
> 语义：`IdempotencyGuard` 用 **INSERT 撞唯一键**占位（不是先查后写）；命中 COMPLETED → **重放存的响应原文**；命中 IN_PROGRESS → 409 拒绝并发重复；键相同但 `request_hash` 不同 → 409（键被挪用）。`FAILED` 允许用原键重试（`reclaim` 回 IN_PROGRESS，条件更新避免竞态）。`IdempotencySweeper` 把过期仍 `IN_PROGRESS` 的键刷成 `FAILED`。见 ADR-0005、ADR-0007。

> **时间戳精度**：凡 `TIMESTAMP(n)` 列，默认值一律写成 `CURRENT_TIMESTAMP(n)`（MySQL 要求两者精度一致，写裸的会报 1067）。见 ADR-0008。

## 5. 接口契约

### 身份
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | `customerId` + PIN 建会话；未知客户与错误 PIN 共用一条消息，不能被用来枚举客户 |
| POST | `/api/auth/logout` | 销毁会话 |
| GET | `/api/auth/me` | 当前会话的客户；未登录 `401` |
| GET | `/api/auth/csrf` | 取 CSRF token，并写下可读的 `XSRF-TOKEN` cookie |

> 身份一律来自**会话**，不由请求头携带；`@CurrentCustomer` 从会话解析客户，匿名会话在进 handler 之前就 `401`。写操作要求 `X-XSRF-TOKEN` 头。

### 对话与助手
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/assistant/conversations` | 新对话：创建 Conversation，返回 id |
| GET | `/api/assistant/conversations?includeArchived=true` | 列出当前客户的对话；每项带 `status`、派生 `state` 与正在跑的 `runId` |
| GET | `/api/assistant/conversations/{id}/messages` | 该对话历史（含每张卡片的当前状态） |
| POST | `/api/assistant/conversations/{id}/messages` | 发消息（同步入口）；只读工具直接执行、结果由服务端渲染成人话并入回复（原始负载只随 `executed` 出去，见 ADR-0015），变更工具落 **PendingAction**；会话忙时 `409` |
| POST | `/api/assistant/chat?conversationId=` | 便捷入口：不带 `conversationId` 即新开一段对话；响应回带 `conversationId`。幂等键：请求头 `Idempotency-Key` |
| GET | `/api/assistant/conversations/{id}/stream?message=` | **SSE**：`token` 事件流式吐字，最后一发 `done` 带完整结果（含卡片）；**不做幂等**；池打满先回 `503 SERVICE_BUSY`，首字节前失败整条重放 |
| GET | `/api/assistant/conversations/{id}/invocations` | 该对话的模型调用审计；归属同历史，他人会话 `403` |
| POST | `/api/assistant/actions/{token}/confirm` | 归属 → 行锁 → 未过期 → 未处理 → 事务内执行变更工具；重复确认返回 `replayed:true` |
| POST | `/api/assistant/actions/{token}/reject` | 标记 REJECTED（重复拒绝也是 `replayed:true`） |

> 幂等键走请求头 **`Idempotency-Key`**（可省；省了就是"不做幂等保护"）。已接的入口：`POST /api/orders`（`CREATE_ORDER`）、`POST /api/assistant/chat` 与 `POST .../{id}/messages`（`SEND_MESSAGE`）。确认/拒绝**不用**这个头——token 本身就是唯一标识（见 ADR-0007）。
> 越权与不存在统一处理：访问他人的会话 `403`、不存在的会话 `404`；用他人的 token 确认 `403`、不存在的 token `404`、已过期 `410`。

### 会话管理
归档、恢复、停止、重订阅、队列与每客户状态流的端点集中在 [会话管理-设计定稿 §4](./会话管理-设计定稿.md)。

### 订单与商品
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/orders` · `/api/orders/{orderNo}` | 分页列表（按会话客户收窄）/ 详情（归属校验） |
| POST | `/api/orders` | 直接下单（幂等键 `Idempotency-Key`） |
| GET | `/api/catalog/items` | 可下单商品（前端卡片展示用） |
| GET | `/swagger-ui.html` | API 文档 |

**ActionCard JSON**（`ChatResponse.actions[]` 与历史 `messages[].action` 同构）：
`{ token, toolName, title, summary, argumentsJson, fields:[{label,value}], confirmEndpoint, rejectEndpoint, expiresAt, status }`
> 卡片的文字全部来自**工具自己**：`ToolSpec` 挂一张 `ToolCard{title, summary, fields}`，与工具的 schema、handler 放在一起——**新增一个工具只改一处**。`summary` 由工具自己的 summariser 生成（如 `创建订单：GADGET-02 × 2、THING-05 × 1`），不是模型的话；`fields` 按工具定制成**业务行**（`createOrder` 每行一对「商品 / 数量」），只有认不出名字、参数无法解析的工具才回退成 `argumentsJson` 的原始键。`ActionCardFactory` 只负责卡片外壳（token、端点、过期、状态）与这层回退。

## 6. AI 集成设计

- **端口/适配器**：业务层依赖 `AiAssistantPort`；`SpringAiAdapter` 实现它（`@Profile("!offline")`），主代码另有 `MockAiAdapter`（`@Profile("offline")`，关键词驱动的桩）供没有 Key 的演示，集成测试复用它。见 ADR-0003。
- **记忆回放**：端口签名是 `respond(customerId, List<ChatMessage> memory)`——**端口本身不知道 Conversation 存在**，它只收一串有序发言。是 `AssistantService` 决定"取这个会话最近 N 条"。
- **Grounding**：每次请求把**模型不得臆造的事实**拼进 system prompt——当前 catalog（sku/名称/单价，ADR-0006）+ **本会话最近一次已确认的订单号**（来源 `pending_actions.result_ref`，按客户 + 会话过滤，ADR-0015）。提示词集中在 `assistant/infrastructure/ai/prompt/`，填数据由 `AssistantGroundingProvider` 做。
- **回复渲染**：只读工具带一个 `ToolReport`（负载 → 给人看的 markdown），回复 = 模型的话 + 渲染块，原始负载不进 transcript（但它就是记忆，所以订单号与金额渲染后仍在）。见 [ADR-0015](./adr/0015-render-readonly-results-server-side.md)。
- **工具白名单**：`ToolRegistry` 注册 `ToolSpec{name, description, inputSchemaJson, mutating, handler, card}`。模型只能返回注册过的工具名，**绝不反射调用、绝不拼 SQL**。
- **工具集**：`queryMyOrders`、`getOrderByNumber`（只读）；`createOrder`、`updateOrderStatus`、`cancelOrder`（变更 → 卡片）。
- **审批闸口**：`ToolCallingChatOptions.builder().internalToolExecutionEnabled(false)` 关闭 Spring AI 的自动执行，模型返回的工具调用原样交给我们分类——自己按 `mutating` 分流：只读的当场执行，变更的落 PendingAction。见 ADR-0001。
- **谁能执行变更 handler**：白名单里**每个工具都带 handler**（包括变更的），`mutating` 标志决定"谁有权扣扳机"——只读 handler 由 `AssistantService` 调用，变更 handler **只有 `ActionConfirmationService` 会调**（`AssistantService` 里根本没有这条路径）。
- **工具返回值契约**：handler 返回 `ToolResult{payloadJson, ref}`——`payloadJson` 是完整结果，`ref` 是稳定标识（如订单号）。重复确认重放直接用 `ref`，不从结果 JSON 里按字段名反解析。
- **超时**：同步读写在 `AiHttpClientConfig` 通过 `RestClientCustomizer` 换上带超时的 `JdkClientHttpRequestFactory`（连接 5s / 读取 60s）；流式在 `SpringAiAdapter` 用 Reactor `.timeout(STREAM_TIMEOUT)` + `.blockLast(STREAM_TIMEOUT)` 双上界。常量都在 `AiCallPolicy`。
- **重试**：阻塞重试是框架自带的 `RetryTemplate`（默认 10 次、退避上限 3 分钟），用 `spring.ai.retry.*` 收到 **3 次 / 1s / ×2 / 上限 8s**；流式框架不重试，`respondStreaming` 自建同款策略，**只在首字节之前**整条重放，首字节之后不再重试（重放会把已吐给客户的字再吐一遍）。两处都**没有 jitter、没有熔断**；重复执行的风险由幂等键与卡片行锁兜住。
- **准入控制**：每客户每分钟发送数与全进程在飞的模型调用数各有上限（`assistant.ai.rate-limit` / `max-concurrent`），超出回 `429 RATE_LIMITED`（带 `Retry-After`），不排队——一个客户的突发不能占满全部工作线程。

## 7. 事务与一致性

- `@Transactional`（Spring 的）**只在 service 层**，**只包住数据库操作**；AI 调用在事务外。见 ADR-0002。
- 有事务：`OrderService`、`ConversationService`、`ActionConfirmationService`。没有事务：`AssistantService`（含 AI 调用）、`IdempotencyGuard`（它保护的动作用可能含 AI 调用）、`ConversationRunQueue`（纯内存）。
- **确认为什么可以且应该在事务里**：确认路径只有"建单/改状态 + 改 pending 状态"这种快操作，没有网络调用，两者必须一起提交；并且要靠同一事务里的 `FOR UPDATE` 行锁来做重复确认的去重。
- 一致性：变更走"确认后执行"，天然规避"AI 成功但本地回滚"——AI 阶段从不写业务表。
- 幂等：**两条路**（ADR-0007）。① 客户端重试 → `idempotency_records`：INSERT 占位，COMPLETED 则重放存储的响应体（连模型调用都不会发生第二次）。② 重复点确认 → `pending_actions` 的 `FOR UPDATE` 行锁 + 状态机：第二次确认拿到锁时状态已是 CONFIRMED，于是走重放。

## 8. 安全

- **身份来自会话，不来自请求头**：登录后客户 id 存在会话里，`@CurrentCustomer` 从会话解析；匿名会话在任何 handler 之前就 `401`。`CurrentCustomer` 处的注释写明了理由——一个客户端可自写的身份头，等于让任何人冒充任何客户（这正是它要堵掉的洞）。
- **一切查询按会话客户收窄**：他人会话/订单按"不存在"或 `403` 处理，调用方无法区分"不属于我"与"不存在"。
- **CSRF**：cookie 会话下写操作要求 `X-XSRF-TOKEN` 头（值取自可读的 `XSRF-TOKEN` cookie），SPA 读 cookie 回填。
- PendingAction `token` **绑定发起客户**，只有本人能确认；`expires_at` 过期即失效。
- AI 只输出"工具名 + 结构化参数"，参数经服务端校验后才执行；**价格由服务端从 catalog 解析**，AI 不可指定金额；工具 schema 里没有 `customerId`，越权在类型上就不可能。
- 日志脱敏；Key 只走环境变量。演示身份是配置里的 `customerId:PIN` 对（`assistant.auth.pins`），**没有用户表**——客户是业务键，不是账号；未知客户与错误 PIN 共用一条错误消息，登录端点不能被用来枚举客户。

## 9. 前端（Vue 3 + Vite + TS）

一个登录页 + 三个视图：**Login**（客户编号 + PIN）、**Assistant**（会话列表侧栏 + 消息流 + 卡片确认 + 新对话 + 队列 + 停止）、**Orders**（分页列表 + 详情）、**Catalog**（商品与单价，用来说明"价格只在这里定义"）。顶栏显示当前客户与「登出」；换一个客户登录即重建每个视图，用来现场演示越权不可见。

**视觉语言**（token 表在 `style.css` 顶部，颜色只承担语义）：**靛蓝 `--authority #1E43B8`** 表示「服务端说了算」——单价、执行按钮、焦点；**紫 `--proposal #6C3FA6`** 只出现在等待授权的确认单上（模型提议、尚未生效），已执行与已拒绝分别是绿与红。三种字体各有固定职责：系统说衬线（助手的话和标题），客户说无衬线，等宽只留给真正的机器数据（sku、订单号、token）。确认单是页面上唯一「响亮」的元素——打孔的撕取边、紫顶线、「待授权」标签、签名线、实时倒计时，确认后落一枚印章。

**构建产物怎么进 static**：`vite.config.ts` 里 `build.outDir` 直接指向 `../backend/src/main/resources/static`（`emptyOutDir: true`），所以 `pnpm build` 一步到位。开发用 `pnpm dev` + Vite proxy → `:8081`。
**为什么前端不是 Maven 模块**：把 Node 塞进默认 `mvn package` 会让构建强依赖本机 Node 版本，而 Dockerfile 本来就用独立的 node 阶段构建前端。默认构建完全不碰 Node；需要"一条命令出全栈包"时用 `mvn -Pfrontend package`。
**状态从哪来**：会话列表与运行态由一个**零依赖**的模块级单例 store（`useSessionStore`，前端运行时依赖仍只有 `vue` 一个）承载，`AssistantView` 是它的视图；`api.ts` 里用 `fetch` + `ReadableStream` 解析 SSE（要带会话 cookie 与 CSRF 头，`EventSource` 做不到），`401` 一律回登录页。见 [ADR-0014](./adr/0014-conversation-state-is-pushed.md)。

## 10. 工程化与测试

统一异常(`@RestControllerAdvice` + 统一响应体) · 参数校验(`@Valid` + 自定义) · 日志 · API 文档(springdoc + Swagger UI) · 格式化(Spotless + Prettier，绑定在构建里，先格式化再编译)。

测试分六层（L1–L6，完整分层表见 [README「测试」](../README.md)）。**默认 `mvn test` 全部能跑、不烧 API 配额**——但集成层跑在真实 MySQL 8 上，**需要常驻测试容器**（`make db-up` 起 `ordermgt-mysql`，独立库 `ordermgt_test`，每类 `clean`+`migrate` 重建 schema）。桩模型替换 `AiAssistantPort`（`@Primary`）——这正是 ADR-0003 那个端口带来的可直接测试性。L5/L6 是各自独立的命令（`make test-frontend` / `make test-e2e`，见 README）。

## 11. 容器化

`Dockerfile` 三阶段：**node 构建 SPA** → **maven 构建 jar（把上一阶段的 static 拷进去）** → **精简 JRE 运行时**（非 root、`MaxRAMPercentage=75`、`HEALTHCHECK` 打 `/actuator/health`）。Node 因此永远不进最终镜像，也不进默认 Maven 构建。
`docker-compose.yml`：`mysql`(healthcheck 用 `mysqladmin ping -h 127.0.0.1`，**必须走 TCP**) + `app`(`depends_on: service_healthy`)。模型 Key 没有默认值——缺 Key 就启动失败，而不是拿占位符去调模型。
