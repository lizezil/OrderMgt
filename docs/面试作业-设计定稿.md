## 4. 领域模型与数据库（Flyway）

**聚合与关系**：`Order`(聚合根) ── 1..* `OrderLine`；`Conversation`(聚合根) ── 1..* `Message` ── 0..1 `PendingAction`；`CatalogItem` 被 `OrderLine` 引用（按 sku）。

### `catalog_items` — 价格的唯一来源
`id` PK · `sku` UNIQUE · `name` · `unit_price DECIMAL(12,2)` · `active BOOL` · `created_at`
> 5 条种子数据（Flyway）。**AI 只选商品与数量，永不提供价格**——这是关键完整性规则。

### `orders`
`id` PK · `order_no` UNIQUE · `customer_id` · `status`(CREATED/COMPLETED/CANCELLED) · `total_amount DECIMAL(12,2)` · `created_at` · `updated_at`
索引 `(customer_id, created_at DESC)`
> 幂等**不在这张表上**——由 `idempotency_records` 承担，业务聚合保持干净。

### `order_lines`
`id` PK · `order_id` FK→orders · `sku` · `item_name` · `quantity INT CHECK>0` · `unit_price` · `line_amount`
索引 `(order_id)`

### `conversations` — 记忆的边界
`id` PK · `customer_id` · `title`（首条用户消息截断；可 AI 生成）· `status`(ACTIVE/ARCHIVED) · `created_at` · `updated_at` · `last_message_at`
索引 `(customer_id, last_message_at DESC)`
> **"新对话" = 新建一行 Conversation**；旧对话保留，可回看。

### `messages` — 记忆的内容
`id` PK · `conversation_id` FK · `role`(CUSTOMER/ASSISTANT/TOOL) · `content VARCHAR(8000)` · `pending_action_id NULL` · `created_at`
索引 `(conversation_id, id)`
> 记忆 = 取该对话**最近 N 条**（默认 **N=20**，可配 `assistant.memory.window`）按时间正序回填给模型；不跨 Conversation。
> 实现细节：`findRecentMessages` 用 `ORDER BY id DESC LIMIT N` 再在内存里反转（两个方言都支持的写法）。`content` 必须是 `VARCHAR(8000)`（为保证 H2/MySQL 同脚本可移植，没用 TEXT）；只读工具结果可能很长，因此落库前在 `Message` 里**按 8000 截断**——超长直接 INSERT 会被数据库拒绝，这是必须的，不是优化。
> 只读工具的结果目前**内联在 ASSISTANT 消息里**（`[queryMyOrders] {...}`），所以下一轮模型能"记得"上一轮查到的内容。实测第 4 轮能答出第 1 轮工具结果里的金额。代价是把原始 JSON 也喂回了模型；正式版应改成"工具结果回灌后让模型总结成自然语言"（M5 之后）。

### `pending_actions` — 确认闭环的载体
`id` PK · `token` UNIQUE · `customer_id` · `conversation_id` · `source_message_id NULL` · `tool_name` · `arguments_json VARCHAR(4000)` · `summary` · `status`(PENDING/CONFIRMED/REJECTED/EXPIRED) · `expires_at` · `resolved_at NULL` · `result_ref NULL`（执行产出的 order_no）· `created_at`
索引 `(customer_id, status, expires_at)`, UNIQUE`(token)`
> `token` 是 **24 字节随机数的 hex**（48 字符，VARCHAR(64) 装得下），是这张卡片的"能力凭证"；但它只够证明"持有 token"，还必须在同一请求里是**发起人本人**（`isOwnedBy`）。
> **这张表不存响应体**，只存 `result_ref`（order_no）。所以重复确认返回的是"已经确认过 + 订单号"（`replayed:true`），而不是第一份响应原文——确认的幂等保证是"不重复执行"，不是"逐字节重放"。想追求逐字节重放就得再加 `response_json`，暂时不值这个列宽。
> `expires_at` 在**读取时**判断（confirm/reject 都会查），所以即使清理任务没跑，过期卡片也执行不了；另有一个 `PendingActionSweeper`（`@Scheduled`，默认 60s）把超时行批量刷成 `EXPIRED`，让状态列说真话。
> `arguments_json` 是 VARCHAR(4000)；`PendingAction.propose` 对超长参数**直接拒绝**（抛 VALIDATION_FAILED），不截断——截断会造出一个"能执行但是错的"动作。

### `ai_invocations` — 审计与可观测
`id` PK · `conversation_id NULL` · `customer_id` · `model` · `prompt_tokens` · `completion_tokens` · `latency_ms` · `outcome`(OK/ERROR/TIMEOUT) · `error NULL` · `tool_calls_json NULL` · `created_at`
> 与 `messages` 分工：`messages` 给用户看，`ai_invocations` 给运维/审计看。**当前未写入**（M3–M5 只把 token 数回给了响应体），是留给可观测性的位置。

### `idempotency_records` — 通用幂等
`id` PK · `customer_id` · `operation`(SEND_MESSAGE/CREATE_ORDER) · `idempotency_key` · `request_hash NULL` · `status`(IN_PROGRESS/COMPLETED/FAILED) · `result_ref NULL` · `response_json NULL` · `created_at` · `completed_at NULL` · `expires_at NULL`
UNIQUE `(customer_id, operation, idempotency_key)`；索引 `(expires_at)`
> 语义：`IdempotencyGuard` 用 **INSERT 撞唯一键**占位（不是先查后写）；命中 COMPLETED → **重放 `response_json` 原文**；命中 IN_PROGRESS → 409 拒绝并发重复；键相同但 `request_hash` 不同 → 409（键被挪用）。`FAILED` 允许用原键重试（`reclaim` 回 IN_PROGRESS）。见 ADR-0005、ADR-0007。

## 5. 接口契约

### 对话与助手
| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| POST | `/api/assistant/conversations` | **新对话**：创建 Conversation，返回 id | ✅ M4 |
| GET | `/api/assistant/conversations` | 列出当前 Customer 的对话（按 `last_message_at` 倒序） | ✅ M4 |
| GET | `/api/assistant/conversations/{id}/messages` | 该对话历史（用于前端回填） | ✅ M4 |
| POST | `/api/assistant/conversations/{id}/messages` | 发消息。只读工具直接执行返回结果；变更工具落 **PendingAction** 并返回 `actions[]` 卡片 | ✅ M5 |
| POST | `/api/assistant/chat?conversationId=` | **便捷入口**：不带 `conversationId` 即新开一段对话；响应回带 `conversationId` | ✅ M4 |
| GET | `/api/assistant/conversations/{id}/stream` | **SSE**：`token` 事件流式吐字，最后一发 `done` 带与 JSON 接口同构的结果（含卡片）；**不做幂等** | ✅ M7 |
| POST | `/api/assistant/actions/{token}/confirm` | 归属 → 行锁 → 未过期 → 未处理 → 事务内执行变更工具；重复确认返回 `replayed:true` | ✅ M5 |
| POST | `/api/assistant/actions/{token}/reject` | 标记 REJECTED（重复拒绝也是 `replayed:true`） | ✅ M5 |

> 幂等键走请求头 **`Idempotency-Key`**（可省；省了就是"不做幂等保护"）。已接的入口：`POST /api/orders`（`CREATE_ORDER`）、`POST /api/assistant/chat` 与 `POST .../{id}/messages`（`SEND_MESSAGE`）。确认/拒绝**不用**这个头——token 本身就是唯一标识（见 ADR-0007）。
> 越权与不存在统一处理：访问他人的会话返回 **403**，不存在的会话 **404**；用他人的 token 确认返回 **403**，不存在的 token **404**，已过期 **410**（均实测）。
> 请求头一律带 `X-Customer-Id`。

### 订单与商品
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/orders` | 分页（按 customerId 收窄） |
| GET | `/api/orders/{orderNo}` | 详情（归属校验，防越权） |
| GET | `/api/catalog/items` | 可下单商品（前端卡片展示用） |
| GET | `/swagger-ui.html` | API 文档 |

**ActionCard JSON**（`ChatResponse.actions[]` 与历史 `messages[].action` 同构）：
`{ token, toolName, title, summary, argumentsJson, fields:[{label,value}], confirmEndpoint, rejectEndpoint, expiresAt, status }`
> 卡片的文字全部来自**工具自己**：`ToolSpec` 挂一张 `ToolCard{title, summary, fields}`，与工具的 schema、handler 放在一起——**新增一个工具只改一处**，不必再去别处同步标题、摘要、字段。`summary` 由工具自己的 summariser 生成（如 `创建订单：GADGET-02 × 2、THING-05 × 1`），不是模型的话——卡片必须陈述"实际会执行什么"。`fields` 按工具定制成**业务行**——`createOrder` 每行一对「商品 / 数量」，`updateOrderStatus` 与 `cancelOrder` 给「订单号 / 目标状态」；只有认不出名字、或参数无法解析的工具才回退成 `argumentsJson` 的原始键，所以卡片上不会出现 `lines:[{...}]` 这种参数原文；`ActionCardFactory` 只负责卡片外壳（token、端点、过期、状态）与这层回退，卡片内容一概不问。`status` 让历史里的卡片能显示已确认/已拒绝。

## 6. AI 集成设计

- **端口/适配器**：业务层依赖 `AiAssistantPort`；`SpringAiAdapter` 实现它，`MockAiAdapter` 供测试。见 ADR-0003。
- **记忆回放**：端口签名是 `respond(customerId, List<ChatMessage> memory)`——**端口本身不知道 Conversation 存在**，它只收一串有序发言（CUSTOMER→UserMessage，ASSISTANT→AssistantMessage，TOOL→带前缀的 UserMessage）。是 `AssistantService` 决定"取这个会话最近 N 条"。见 ADR-0003。
- **Grounding**：每次请求把当前 catalog（sku/名称/单价）拼进 system prompt，模型不再把商品名当 sku。见 ADR-0006。
- **工具白名单**：`ToolRegistry` 注册 `ToolSpec{name, description, inputSchemaJson, mutating, handler, card}`（`card` 为 `ToolCard{title, summary, fields}`，只有变更工具有）。模型只能返回注册过的工具名，**绝不反射调用、绝不拼 SQL**。
- **工具集**：
  - `queryMyOrders`（只读）· `getOrderByNumber`（只读）
  - `createOrder(lines:[{sku, quantity}])`（变更 → 卡片）
  - `updateOrderStatus(orderNumber, targetStatus)`（变更 → 卡片）
  - `cancelOrder(orderNumber)`（变更 → 卡片）
- **审批闸口**：`ToolCallingChatOptions.builder().internalToolExecutionEnabled(false)` 关闭 Spring AI 的自动执行，模型返回的工具调用原样交给我们分类——**我们不跑 `ToolCallingManager` 循环**，而是自己按 `mutating` 分流：只读的当场执行，变更的落 PendingAction。见 ADR-0001。
- **谁能执行变更工具的 handler**：白名单里**每个工具都带 handler**（包括变更的），`mutating` 标志决定"谁有权扣扳机"——只读 handler 由 `AssistantService` 调用，变更 handler **只有 `ActionConfirmationService` 会调**（`AssistantService` 里根本没有这条路径）。把 handler 留空、再在确认侧另建一套执行器，会让"这个工具能做什么"散落两处。
- **工具返回值契约**：handler 返回 `ToolResult{payloadJson, ref}`——`payloadJson` 是完整结果（只读工具给模型看、变更工具给调用方），`ref` 是这次动作产出的稳定标识（如订单号）。重复确认重放时直接用 `ref`，**不必再从结果 JSON 里按字段名 `orderNo` 反解析**：工具产出的形状从此写在接口上，而不是只存在于一句口头约定。
- **超时/重试**：连接/读取超时显式配置；有限重试 + 指数退避，**只用于只读调用**；变更操作靠幂等键兜底。（**未实现**：目前依赖 DashScope 客户端默认超时，没有显式退避。）
- **容错解析**：工具参数按字段逐个校验（`requireText`/`parseLines`），结构非法时**不执行并报 400**；`ActionCardFactory.summaryOf` 对无法描述的参数降级成工具名，保证"无法描述"的提议仍能以卡片形式被拒绝，而不是 500。

## 7. 事务与一致性

- `@Transactional`（Spring 的）**只在 service 层**，**只包住数据库操作**；AI 调用在事务外。见 ADR-0002。
- 三个事务边界的实际归属：`OrderService` / `ConversationService` / `ActionConfirmationService` 是 `@Transactional`；`AssistantService`（含 AI 调用）**不是**；`IdempotencyGuard` **也不是**（它保护的动作用可能含 AI 调用）。`PendingAction` 的占位插入与卡片消息各自短事务提交。
- **确认为什么可以且应该在事务里**：确认路径只有"建单/改状态 + 改 pending 状态"这种快操作，没有网络调用，两者必须一起提交；并且要靠同一事务里的 `FOR UPDATE` 行锁来做重复确认的去重。
- 一致性：变更走"确认后执行"，天然规避"AI 成功但本地回滚"——AI 阶段从不写业务表。
- 幂等：**两条路**（见 §4 与 ADR-0007）。① 客户端重试 → `idempotency_records`：`IdempotencyGuard` 用 INSERT 占位，COMPLETED 则重放存储的响应体（连模型调用都不会发生第二次——实测两次调用的 `promptTokens` 完全相同，证明第二次是重放）。② 重复点确认 → `pending_actions` 的 `FOR UPDATE` 行锁 + 状态机：第二次确认拿到锁时状态已是 CONFIRMED，于是走重放而不是再执行一次。

## 8. 安全

- 一切查询按 `X-Customer-Id` 收窄 → **演示 AI 无法越权查/改他人订单**（IDOR 防护）。
- PendingAction `token` **绑定发起 Customer**，只有本人能确认；`expires_at` 过期即失效。
- AI 只输出"工具名 + 结构化参数"，参数经服务端校验后才执行；**价格由服务端从 catalog 解析**，AI 不可指定金额。
- 日志脱敏；Key 只走环境变量。

## 9. 前端（Vue 3 + Vite + TS）

三个视图：**Assistant**（会话列表侧栏 + 消息流 + 卡片确认 + **"新对话"按钮**）、**Orders**（分页列表+详情）、**Catalog**（商品与单价，用来说明"价格只在这里定义"）。顶栏可切换 `X-Customer-Id`，用来现场演示越权不可见。

**视觉语言**（token 表在 `style.css` 顶部，颜色只承担语义）：**靛蓝 `--authority #1E43B8`** 表示「服务端说了算」——单价、执行按钮、焦点；**紫 `--proposal #6C3FA6`** 只出现在等待授权的确认单上（模型提议、尚未生效），已执行与已拒绝分别是绿与红。三种字体各有固定职责：系统说衬线（`Georgia` + 宋体，助手的话和标题像印出来的），客户说无衬线，等宽只留给真正的机器数据（sku、订单号、token）。确认单是页面上唯一「响亮」的元素——打孔的撕取边、紫顶线、「待授权」标签、签名线、实时倒计时，确认后落一枚印章；其余部分保持安静。

**构建产物怎么进 static**：`vite.config.ts` 里 `build.outDir` 直接指向 `../backend/src/main/resources/static`（`emptyOutDir: true`），所以 `pnpm build` 一步到位，不需要额外的拷贝脚本。开发用 `pnpm dev` + Vite proxy → `:8081`。

**为什么前端不是 Maven 模块**：把 Node 塞进默认 `mvn package` 会让构建强依赖本机 Node 版本，而 Dockerfile 本来就要用独立的 node 阶段构建前端（§11）。折中：默认构建完全不碰 Node；需要"一条命令出全栈包"时用 `mvn -Pfrontend package`（`exec-maven-plugin` 调 `pnpm install --frozen-lockfile && pnpm run build`）。
> pnpm 11 默认拦截依赖的 postinstall，`esbuild` 需要显式放行；已用 `pnpm approve-builds --all` 把批准写进 `frontend/pnpm-workspace.yaml`（`allowBuilds: {esbuild: true}`）。少了这步，`pnpm run build` 会在"运行前依赖校验"阶段直接失败——这是个很容易踩、又很难一眼看懂的坑。

**三视图之外没做的事**：没有 vue-router（tab 切换就够），没有状态管理库（一个视图一个 `ref` 就够），没有组件库（自写十几个 CSS 类）。理由：这个规模引入它们只会增加讲解负担。

### 12.1 跑到真 MySQL 才暴露的两个缺陷（都已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 容器启动即 `Application run failed`，Flyway `V1__init.sql` 报 **MySQL Error 1067 `Invalid default value for 'created_at'`** | 列是 `TIMESTAMP(3)`，默认值写的是裸 `CURRENT_TIMESTAMP`（精度 0）。**MySQL 要求两者精度一致**，H2 的 `MODE=MySQL` 却照单全收——所以"portable migration"其实只 portable 到 H2 | 全部改为 `DEFAULT CURRENT_TIMESTAMP(3)`，并在脚本头部把这条约束写成注释（这是最容易漏、又只在真库才炸的坑）。决策与取舍见 [ADR-0008](adr/0008-pin-timestamp-precision-in-migrations.md) |
| 2 | 模型调用失败时接口返回 **500 `INTERNAL_ERROR`（"服务内部错误"）** | 适配器让 Spring AI 的异常直接冒泡，而错误码表里那个 `UPSTREAM_AI_ERROR(502)` 从没被真正抛出过——一个"Key 过期/上游宕机"被报成了"我们的 bug" | 适配器包一层 `callingUpstream(...)` 翻译成 `UPSTREAM_AI_ERROR`（502），现在返回 `{"code":"UPSTREAM_AI_ERROR","message":"AI 服务调用失败"}` |

> 这两条正是"必须跑真目标库/真上游才算验证"的例证：H2 与桩模型都放过了它们。第 1 条若没在容器里跑，交付物在面试方机器上第一次 `up` 就会失败。
