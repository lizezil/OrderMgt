# 面试讲解手册：Order Assistant

> 这份手册面向**交付后的追问面试**：面试官拿着作业，一条一条问。它把「原始要求 → 我做在哪 → 项目结构 → 实现细节 → 怎么讲 → 可能被问什么」一次讲透，并给出 8 分钟演示脚本。
>
> 所有事实都对照过当前代码（Spring Boot **3.5.16** / Spring AI **1.1.8** / 迁移 **V1–V4** / ADR **0001–0015**）。
> 一条铁律：**能跑通的才讲，讲了就要能翻到代码。** 面试最忌讳"文档里有、代码里没有"。

---

## 1. 一句话定位

> 「这是一个订单管理服务：客户用自然语言让 AI 助手**查**自己的订单，**并在确认后**才真正创建或变更订单。
> 核心不是『接上了大模型』，而是**接上之后怎么保证它不闯祸**——模型只能选商品和数量，金额由服务端定；任何会改数据的操作都只生成一张卡片，客户点确认才执行。**因为模型的输出是不可信输入。**」

按这个顺序讲，面试官的问题会自动落在你准备过的地方：安全边界 + 一致性，而不是"我调了个 API"。

## 3. 项目结构：怎么讲"结构清晰"

```
        ┌───────────────────────────────────────────────┐
        │  api/          控制器 + DTO(record) + ApiMapper │  ← HTTP 边界
        └───────────────┬───────────────────────────────┘
                        │ 依赖
        ┌───────────────▼───────────────────────────────┐
        │  application/  用例编排 + @Transactional 边界   │  ← 事务边界
        └───────────────┬───────────────────────────────┘
                        │ 依赖
        ┌───────────────▼───────────────────────────────┐
        │  domain/       实体/值对象/端口，零框架依赖     │  ← 业务规则
        └───────────────▲───────────────────────────────┘
                        │ 实现端口
        ┌───────────────┴───────────────────────────────┐
        │  infrastructure/  MyBatis-Plus 持久化、Spring AI │  ← 技术细节
        └───────────────────────────────────────────────┘
```

一句话：**`api → application → domain`，`infrastructure → domain`（实现端口），domain 不依赖任何框架。**

| 包 | 职责 | 关键类 |
|---|---|---|
| `shared/` | 跨领域共享，不含业务规则 | `ApiResponse`、`PageResult`、`ErrorCode`、`GlobalExceptionHandler` |
| `config/` | 装配 | `MyBatisPlusConfig`、`OpenApiConfig`、`AsyncConfig`（流式线程池）、`AiHttpClientConfig`（超时） |
| `security/` | 会话认证与 CSRF | `SecurityConfig`、`AuthController`、`PinAuthenticationProvider`、`CurrentCustomerResolver` |
| `idempotency/` | 通用幂等组件（技术关注点，跨用例复用） | `IdempotencyGuard`、`IdempotencySweeper` |
| `catalog/` | 商品目录——**价格的唯一来源** | `CatalogRepository`、`CatalogController` |
| `order/` | 订单核心域 | `Order`(聚合根)、`OrderLine`、`OrderNumber`、`Money`、`OrderService` |
| `assistant/` | 助手领域：记忆、工具白名单、待确认动作、确认闭环、Run | `AssistantService`、`ActionConfirmationService`、`ConversationService`、`SpringAiAdapter`、`ToolRegistry`、`ConversationRunQueue` |

**为什么"单模块 + 领域分包"，而不是微服务全家桶 / 多模块**（这是原题埋的坑）：技术清单里列了 Spring Cloud，却明说"单体演示即可"。

> 说法：「两天时间上 Nacos/Gateway/多模块，只会让主链路跑不通、讲解负担翻倍。所以我用**单 Maven 模块 + 按领域分包**：包的边界就是未来的服务边界，但今天不为它付出分布式代价。**领域分包让依赖方向可验证**——domain 包 import 里出现 `org.springframework` 就是违规。」

### 一处**刻意**的例外（主动说，显示你想过依赖）

`assistant/infrastructure/ai/tools/OrderToolDefinitions` 把只读工具接到 `order.application.OrderService` 上——这是 `infrastructure → application` 的一条边。

> 说法：「工具定义本质是**装配代码**（哪个工具名对应哪个业务用例），这条边是单向的：`order` 侧不反向依赖 `assistant`，不构成环。全仓仅此一处，且有注释说明。」

## 4. 实现细节：一次请求的完整旅程（讲顺这条 = 讲顺 80%）

以**流式入口**为例（它包含同步入口没有的排队/投递逻辑），从浏览器点击到 `done`：

| # | 发生了什么 | 代码位置 | 事务？ |
|---|---|---|---|
| 1 | 前端带会话 cookie 起 `fetch`，读 `ReadableStream` 分帧 | `frontend/src/api.ts#chatStream` | — |
| 2 | 控制器**先校验归属**（越权的请求连"忙不忙"都不能知道），再进队列 | `ConversationController#stream` → `conversationService.getOwned` | 只读事务 |
| 3 | **排队**：该会话已有 Run 在跑就 FIFO 入队（深度 5，满了 429 `QUEUE_FULL`）；空闲则立刻起 | `ConversationRunQueue#submitStreaming` | 无 |
| 4 | `prepare`：拿到/新建会话 → **先把客户消息提交入库** → 组装最近 20 条记忆 | `AssistantService#prepare` | 三个短事务 |
| 5 | 开一条 `RUNNING` 的 `Run` 落库 | `AssistantService#executeTurn` → `runRepository.save(Run.start(...))` | 短事务 |
| 6 | **调模型（无事务！）**：流式增量通过 `onTextDelta` 逐字推给前端 `token` 事件 | `SpringAiAdapter#respondStreaming` | **无**（ADR-0002） |
| 7 | 模型返回后 `complete`：遍历工具调用**按 `mutating` 分流**——只读当场执行、变更落卡片 | `AssistantService#complete` | 若干短事务 |
| 8 | 回执 `done` 事件带与 JSON 接口**同构**的结果（含卡片）；关 Run 为 `COMPLETED` | `ConversationController#streamTurn` | 短事务 |
| 9 | 每次模型调用往 `ai_invocations` 落一行审计（成功/失败都写） | `AssistantService#recordSuccess/recordFailure` | 旁路，写失败只 warn |

**这条链路里能自然引出 5 个考点**：第 2 步→越权防护（§7）；第 3 步→会话级并发控制（§8）；第 4/6/9 步→**AI 不进事务**、审计旁路（§5.2、§6）；第 5/6 步→Run 层与"客户消息先落库"（§8）；第 7 步→**审批闸口**（§5.1）。

## 5. 五个"这道题真正在考的点"

### 5.1 AI 输出是不可信输入 → 审批闸口（最重要，一定被问）

**题目原文的陷阱**：让 AI "决定调用哪个业务方法"。若直接把模型返回的函数名反射调用或拼 SQL，等于把控制权交给一个可被提示注入的模型。这是本题**最大的坑**。

**三层做法**：

1. **关掉框架的自动执行**：`ToolCallingChatOptions.builder().internalToolExecutionEnabled(false)`——工具调用原样交回来，我拿到决定权。
2. **白名单**：`ToolRegistry` 只注册 5 个工具（`queryMyOrders`/`getOrderByNumber` 只读，`createOrder`/`updateOrderStatus`/`cancelOrder` 变更）。模型返回未注册的工具名 → 直接 `UPSTREAM_AI_ERROR`。
3. **结构上就执行不了变更**：`AssistantService` 只调用只读 handler；变更 handler **只有 `ActionConfirmationService` 能调**——这个类里根本没有执行变更的路径。

> 追问「为什么不直接 `internalToolExecutionEnabled(true)`？」答：「那样'执行'发生在框架内部，我拿不到决定权。**审批闸口必须在我这侧，不能指望模型自律。**」

### 5.2 AI 调用绝不进数据库事务（ADR-0002）

**反例**：模型可能跑好几秒，事务里握着数据库连接等它 → 连接池被打满、锁等待、级联故障；而且"AI 成功但本地回滚"会让两边状态不一致。

**顺序**：事务外调模型 → 收获结果 → 短事务写业务表。「AI 成功但本地失败」这类不一致，由**变更操作走"确认后执行"**天然规避——AI 阶段从不写业务表。

**谁有 `@Transactional`，谁没有**（背熟）：

| 有事务 | 没有事务 |
|---|---|
| `OrderService`（建单+明细一起） | `AssistantService`（含 AI 调用） |
| `ConversationService`（记忆读写） | `IdempotencyGuard`（它保护的动作可能含 AI 调用） |
| `ActionConfirmationService`（**可以**在事务里：确认路径只有建单/改状态，无网络调用，且要靠 `FOR UPDATE` 行锁去重） | `ConversationRunQueue`（纯内存） |

### 5.3 价格只有一个来源 + grounding（ADR-0006，有一个真实故事）

**规则**：模型只能给 `sku` 和 `quantity`；`createOrder` 的工具 schema 里**根本没有价格字段**；金额由 `OrderService#resolveLines` 从 `catalog_items` 解析。

**真实故事（讲这个最加分）**：实测让模型下 3 个 Widget，它返回 `{"sku":"Widget"}`，而真实 sku 是 `WIDGET-01`——**模型把商品名当成了 sku**。修法是每次请求把当前 catalog（sku/名称/单价）拼进 system prompt（grounding）；另一条兜底是"宁可失败也不猜"：sku 不在目录里就 400。

> 注意 grounding 和"价格由服务端解析"是两件事：前者解决模型**选错 sku**，后者解决模型**报错价**。两者都不能省。

### 5.4 幂等有两条路，各司其职（ADR-0005 / 0007）

| 触发场景 | 机制 | 关键实现 |
|---|---|---|
| **客户端重试**（超时后重发） | `idempotency_records` 表，键 `(customer_id, operation, key)` | `IdempotencyGuard` 用 **INSERT 撞唯一键**占位，不是先查后写 |
| **重复点确认**（手滑点两次） | `pending_actions` 的**行锁 + 状态机** | `ActionConfirmationService` 的 `SELECT ... FOR UPDATE` + `PendingAction.adjudicate` |

**必须能说清的细节**：

- 命中 `COMPLETED` → **重放存储的响应原文**（连模型都不会再调一次——实测两次 `promptTokens` 相同，证明第二次是重放）。
- 键相同但请求体哈希不同 → 409（**键被挪用**）。
- 命中 `IN_PROGRESS` → 409（拒绝并发重复）。
- `FAILED` 允许用原键重试（`reclaim` 回 `IN_PROGRESS`，条件更新避免竞态）。
- 「动作已提交、标记未写入」之间崩溃 → 键卡在 `IN_PROGRESS`，由 `IdempotencySweeper` 过期后刷成 `FAILED`；若连响应体都存不进 → `RESULT_UNKNOWN` 封印，绝不让重试再跑一次（会重复下单）。

### 5.5 解耦：AI 藏在端口后面（ADR-0003，对应加分项①）

- 业务只依赖 `AiAssistantPort.respond(customerId, List<ChatMessage> memory)`——**端口本身不知道"会话"存在**，它只收一串有序发言。
- `SpringAiAdapter`（`@Profile("!offline")`）实现真实调用；`MockAiAdapter`（`@Profile("offline")`，关键词驱动）供没有 Key 的演示，**集成测试复用它**（测试行为与演示一致，且不烧配额）。
- 直接收益：**测试可以直接替换成桩**，不需要 mock 框架深处的东西。

## 6. 健壮性：超时 / 重试 / 审计 / 准入（题目明示的考察点）

| 维度 | 做法 | 关键数字 |
|---|---|---|
| **超时（同步）** | `RestClientCustomizer` 换上带超时的 `JdkClientHttpRequestFactory` | 连接 5s / 读取 60s |
| **超时（流式）** | Reactor `.timeout()` + `.blockLast()` 双上界 | 2 分钟 |
| **重试（阻塞）** | **框架自带**的 `RetryTemplate`，用属性收窄 | 3 次 / 1s / ×2 / 上限 8s（默认是 10 次、上限 3 分钟） |
| **重试（流式）** | 自建同款退避，**仅首字节前整条重放**，首字节后不重试 | 3 次 / 1s / ×2 / 上限 8s |
| **失败归类** | 三种超时形态（Reactor/`SocketTimeout`/`HttpTimeout`）→ `TIMEOUT`，其余 → `ERROR` | 对外 502 `UPSTREAM_AI_ERROR` |
| **审计** | 每次调用写一行 `ai_invocations`（成功/失败都写），读取走 `GET .../invocations` | 旁路，写失败只 warn |
| **准入** | 每客户每分钟发送数、全进程在飞模型调用数各有上限 | 超出 429 `RATE_LIMITED` + `Retry-After`，不排队 |

> 追问「为什么不重试到底 / 为什么没有熔断？」答：「重试会把已吐给客户的字再吐一遍，所以流式首字节后不重试。没有 jitter、没有熔断——**重复执行的风险由幂等键与卡片行锁兜住**，而不是靠重试策略。这是权衡，我写在已知缺口里。」

## 7. 安全与越权（演示价值最高的一块）

- **身份来自会话，不来自请求头**：登录后客户 id 存在会话里，`@CurrentCustomer` 从会话解析；匿名会话在进 handler 之前就 `401`。旧实现用 `X-Customer-Id` 头，那等于让任何人自称任何客户——这正是被改掉的原因。
- **一切查询按会话客户收窄**：他人会话/订单返回 403 或按"不存在"处理（404），调用方**无法区分**"不属于我"和"不存在"。
- **CSRF**：cookie 会话下写操作要求 `X-XSRF-TOKEN` 头（值取自可读的 `XSRF-TOKEN` cookie）。
- **模型没有传客户 id 的能力**：工具 schema 里没有 `customerId`，`queryMyOrders` 直接用手里的 `customerId`——**越权在类型上就不可能**。
- **卡片 token 绑定发起人**：24 字节随机 hex；知道 token 不够，还必须是同一会话的**本人**（`isOwnedBy`）。
- **演示**：`1001` 登录看自己的单，登出后用 `2002` 登录，账目完全不同；`2002` 拿 `1001` 的 token 确认 → 403。

## 8. 会话与 Run 层

> 原题只要求"多轮记忆"，Run 层是**额外**做的。设计见 [会话管理-设计定稿](会话管理-设计定稿.md) 与 ADR-0011–0014。

| 能力 | 实现 | 依据 |
|---|---|---|
| **Run 落库**：一次"发送→回复"= 一条 Run（`RUNNING`→`COMPLETED`/`FAILED`/`CANCELLED`/`INTERRUPTED`），同步与流式共用一条执行回合 | `AssistantService#executeTurn`、`runs` 表（V3） | ADR-0011 |
| **会话状态派生**：侧栏徽标 `IDLE`/`RUNNING`/`WAITING_APPROVAL` **从 Run + 卡片派生**，不入库 | `ConversationState.derive`、`ConversationService#listFor` | ADR-0011 |
| **重启对账**：启动时把库里残留的 `RUNNING` 标成 `INTERRUPTED` 并补 `ended_at`（一次性 `ApplicationRunner`，不是定时器） | `RunReconciler` | ADR-0011 |
| **忙时入队**：同会话已有 Run 时，流式 FIFO 排队（深度 5 → 429），同步直接 409；排队项可删 | `ConversationRunQueue`、`DELETE .../queue/{itemId}` | ADR-0012 |
| **停止**：`POST .../runs/{runId}/stop` 只对 `RUNNING` 有效且幂等；**真**取消上游流，半截文本落成普通 ASSISTANT 消息，Run 收 `CANCELLED` | `RunRegistry`、`RunService`、`RunCancellation` | ADR-0012 |
| **归档 / 恢复**：只归档"静止"会话（有 Run 或活卡片 → 409），只改可见性、不硬删 | `Conversation.archive/restore` | ADR-0013 |
| **每客户状态流**：`GET /api/assistant/events` 长活 SSE（快照 + 增量），走独立进程内总线，**不占回合池** | `ConversationEventBus`、`EventsController` | ADR-0014 |
| **重订阅运行中的 Run**：首帧当前累积文本快照 + `token` 增量 | `RunRegistry.Handle#attach`、`ConversationController#runEvents` | ADR-0014 |
| **投递尽力而为**：客户端断线只停投递，回合照常跑完并落库；断开**不**触发停止 | `ConversationController#deliver/streamTurn` | ADR-0009 |

**一句话总结**：「Run 层把隐式的'发送→回复'变成有一行记录、有生命周期、能派生状态的东西；它没有违反 ADR-0009（Message 层没有状态列），而是在它之上加了一层。」

## 9. 数据库与迁移

四份迁移（Flyway，`backend/src/main/resources/db/migration/`）：

- **V1__init.sql**：`catalog_items`、`orders`、`order_lines`、`conversations`、`messages`、`pending_actions`、`ai_invocations`、`idempotency_records`
- **V2__orders_add_version.sql**：`orders.version`（乐观锁）
- **V3__runs.sql**：`runs` 表
- **V4__idempotency_response_text.sql**：幂等结果存为文本

| 表 | 一句话 |
|---|---|
| `catalog_items` | **价格的唯一来源**，5 条种子数据 |
| `orders` / `order_lines` | 聚合根 + 明细；幂等**不在这张表上** |
| `conversations` / `messages` | 记忆的边界与内容；"新对话" = 新建一行 conversation |
| `pending_actions` | 确认闭环的载体；`token` 是能力凭证；只存 `result_ref`（订单号），不存响应体 |
| `ai_invocations` | 审计旁路，给运维看（`messages` 给用户看） |
| `idempotency_records` | 通用幂等，键 `(customer_id, operation, key)` |
| `runs` | 一次执行的记录，`(conversation_id, status)` 索引撑住列表查询 |

> **一个讲出去很加分的细节**：`V1` 里 `TIMESTAMP(3)` 列的默认值必须写 `CURRENT_TIMESTAMP(3)`（精度一致），写裸的 `CURRENT_TIMESTAMP` 只有真 MySQL 才会报 1067——兼容模式会放行。这正是本项目**彻底去掉 H2、全程真 MySQL** 的原因（ADR-0008）。

### 11.3 演示：登录 + 五个提问（用 `1001`/`pin 1111` 与 `2002`/`pin 2222`）

|---|---|---|---|
| 0 | 客户 `1001` / PIN `1111` 登录 | 进入助手页 | 身份来自会话，客户端无法自称是别人 |
| 1 | 「我有哪些订单？」 | 气泡里是一段**中文人话**：「你名下有 N 张订单：」+ 每单一块（`` `订单号` `` · 已创建 · ¥金额 · 逐行明细），**没有一坨 JSON** | 只读工具**直接执行**：查的是会话里的客户，模型没有传客户 id 的能力，越权在类型上就不可能。可读性是服务端保证的——渲染由工具自己声明，模型一个字没写也读得通（ADR-0015） |

| 3 | 点「授权执行」 | 卡片变 CONFIRMED、落一枚「已执行」印章；订单页多出那笔单 | 点第二次不会重复下单：卡片状态机 + 行锁 + 幂等键，三道 |

| 5 | 换回 `1001`，再问「我刚才说要下单几个？」 | 答 `3` | 这是**多轮记忆**：按 Conversation 隔离、落库、只回填该会话最近 20 条 |

## 12. 如果面试官说「给我看看代码」

按这个顺序打开，每处都对应一个已被问过无数遍的坑：

1. **`security/SecurityConfig.java` + `CurrentCustomerResolver.java`** — 身份来自会话，没有 header fallback；写操作要 CSRF 头。
2. **`assistant/application/AssistantService.java`** — 编排。它不是 `@Transactional`：**AI 调用绝不进事务**（ADR-0002）。只读工具在这里执行；变更工具**只**调用 `propose()`——这个类里根本没有执行变更 handler 的路径。
3. **`assistant/infrastructure/ai/SpringAiAdapter.java`** — `internalToolExecutionEnabled(false)` 是审批闸口；`systemPrompt()` 每次请求拼进 grounding 事实：catalog（sku/名称/单价，ADR-0006）+ 本会话最近一次已确认的订单号（ADR-0015），由 `AssistantGroundingProvider` 提供、按客户过滤。
4. **`assistant/application/ActionConfirmationService.java`** — `SELECT ... FOR UPDATE` + 状态机，两次并发确认只执行一次。
5. **`infrastructure/ai/tools/OrderToolDefinitions.java`** — 白名单。注意 `createOrder` 的 schema 里**只有 sku 和 quantity，没有价格字段**；只读工具在这里带自己的 `ToolReport`（人话渲染），变更工具带 `ToolCard`——声明挨着 schema 与 handler，加一个工具仍是一次编辑（ADR-0015）。
6. **`idempotency/application/IdempotencyGuard.java`** — 幂等靠 **INSERT 撞唯一键**，不是先查后写；命中 COMPLETED 直接重放存储的响应（连模型都不再调）。
7. **`db/migration/V1__init.sql`** — 一份标准 SQL 直接建目标 MySQL 8；脚本干净到可以在任何 MySQL 上重放。

## 13. 高频追问与答法

| 追问 | 答法（要点） |
|---|---|
| 为什么不直接让模型调工具？ | 那样执行在框架内部，我拿不到决定权；闸口必须在我这侧 |
| 模型瞎编商品编号？ | 实测过（`Widget` vs `WIDGET-01`）；grounding + "宁可失败也不猜" |
| 价格能由模型给吗？ | 不能，schema 里没价格字段，从 `catalog_items` 解析 |
| 重复点确认会下两单吗？ | 不会，`FOR UPDATE` 行锁 + 状态机，第二次走重放 |
| 客户端超时重试呢？ | `Idempotency-Key` → `idempotency_records`，INSERT 占位，COMPLETED 重放 |
| 模型调用的超时和重试？ | 见 §6，注意主动说"重试是框架自带的，我只收窄参数" |
| 幂等表为什么不放 `orders` 上？ | 每个聚合都要带技术簿记，且"查订单"无处安放；独立表通用 |
| AI 调用放事务里有什么问题？ | 握连接等网络调用 → 连接池耗尽；且两边状态可能不一致 |
| 为什么不用 H2 跑测试？ | 它是翻译层不是 MySQL，会放过真库会拒的写法；当年就是这么漏掉 1067 的 |
| `@Transactional` 为什么在 service 层？ | 事务边界是用例边界；DAO 只管一条语句 |
| 为什么要 Conversation 表，不塞进 prompt？ | 记忆需要边界和寿命；也让"回看历史"免费 |
| 回复里那坨 JSON 顾客怎么看？ | 现在没有那坨 JSON 了：只读结果由服务端渲染成人话（订单号 · 中文状态 · ¥金额 · 明细），渲染块自带引导句，所以模型一个字没写的回合也读得通；这份人话就是记忆内容，US-2.1 不回退（ADR-0015） |
| 「刚刚那个订单」它怎么知道？ | 那个订单号只存在于已确认动作的 `result_ref`，transcript 里没有——所以把它作为 **grounding 事实**注入（按客户 + 会话过滤），而不是加一个"查最近一单"的工具，理由同 ADR-0006 |
| 为什么身份不用请求头？ | 头是客户端可写的，等于谁都能冒充谁；会话身份 + CSRF 才挡得住 |
| 这个设计最脆的地方？ | 见 §15 诚实清单（主动报） |

## 14. 题目本身埋的坑（坑位分析）

### A. 隐藏考察点

| # | 坑点 | 说明 |
|---|---|---|
| A1 | **AI 输出 = 不可信输入** | 题目鼓励"让 AI 决定调用哪个业务方法"。真把 LLM 返回的函数名/参数直接反射调用或拼 SQL，等于把控制权交给一个可被提示注入的模型。**本题最大的坑**。 |
| A2 | **"一致性 / 逻辑闭环"是重点词** | 评审一定会看你怎么处理"AI 成功但本地失败 / 本地成功但 AI 超时"。 |
| A3 | **"单体即可" vs 推荐 Spring Cloud** | 诱导你过度设计（Nacos、Gateway、多模块拆分）。两天内上全家桶 = 主链路跑不通。 |
| A4 | **"配备 AI IDE，考察人与 AI 的结合能力"** | 反向的坑：AI 生成的代码你若讲不清、改不动，现场会露怯。 |
| A5 | **API Key 明文给出** | 安全意识测试点。硬编码进代码或提交仓库是最典型的减分项。 |
| A6 | **"Function Calling 或直接业务处理"** | 措辞很松，容易以为二者等价；Function Calling 的工程复杂度远高。 |

### B. 一致性与事务（P0 级坑）

| # | 坑点 | 做法 |
|---|---|---|
| B1 | 在 `@Transactional` 里调 AI | AI 走网络，会长时间持有连接和行锁 → 连接池耗尽。**AI 调用放事务外**，拿到结果再开短事务写库。 |
| B2 | AI 成功但本地回滚 | 变更走"确认后执行"，AI 阶段从不写业务表，天然规避。 |
| B3 | 本地成功但 AI 超时（其实 AI 已成功） | 重试会重复执行 → **幂等键**。 |
| B4 | 重试非幂等操作 | 写操作带幂等键；读/写区分对待。 |
| B5 | SSE 持有长连接 | SSE 期间**不开事务**、不占请求线程做阻塞循环；结束再落库。 |

### C. AI 集成的健壮性

| # | 坑点 | 做法 |
|---|---|---|
| C1 | LLM 返回非法 JSON | 工具参数按字段逐个校验（`requireText`/`parseLines`），非法即拒绝。 |
| C2 | 超时 / 重试 / 退避 / 熔断缺失 | 见 §6：显式超时、收窄的有限重试；无 jitter、无熔断（记入缺口）。 |
| C3 | 非确定性导致测试不稳定 | 接口抽象 + `MockAiAdapter` 桩，单测不打真实 API。 |
| C4 | 配额 / 成本 | 桩跑测试；准入限制每客户与全局在飞调用数。 |
| C5 | DashScope 接入细节 | 用 OpenAI 兼容模式；"流式 + Function Calling"是已知复杂点。 |

### D. 架构与工程

| # | 坑点 | 做法 |
|---|---|---|
| D1 | Spring Boot 3 = `jakarta.*` | 抄旧示例会编译失败。 |
| D2 | API 文档别用 SpringFox | 用 springdoc-openapi。 |
| D3 | Flyway 与 `ddl-auto` 冲突 | 用 Flyway 就设 `ddl-auto=validate`/`none`。 |
| D4 | WebFlux + JPA 阻塞冲突 | 用 Spring MVC 的 `SseEmitter` 更省事。 |
| D5 | Docker 启动顺序 | `healthcheck` + `depends_on: service_healthy`。 |
| D6 | 集成测试依赖常驻 MySQL | 用本机常驻容器 + 独立库 `ordermgt_test`，每类 `clean`+`migrate`。 |
| D7 | Lombok + MapStruct 顺序 | 需要 `lombok-mapstruct-binding`。 |
| D8 | 别用 H2 顶替 MySQL | 见 ADR-0008：兼容模式会放过真库会拒的写法。 |
| D9 | AI 适配层要真解耦 | 端口 `AiAssistantPort`，业务只依赖接口。 |
| D10 | 参数校验要覆盖 AI 来源的数据 | 业务规则和权限在服务端**再校验一遍**。 |

### E. 安全

| # | 坑点 | 做法 |
|---|---|---|
| E1 | AI 驱动的越权查询（IDOR） | 数据权限按**会话客户**强制收窄。 |
| E2 | 禁止 AI 直接触达 SQL / 反射 | 工具白名单 + 参数强类型校验，绝不执行模型给的 SQL/类名/方法名。 |
| E3 | 危险操作需二次确认 | 删除、退款、改价等不可逆动作必须人工确认或直接禁止。 |
| E4 | 日志泄露敏感信息 | 脱敏后再打日志，别把 Key 打进日志。 |
| E5 | 凭证管理 | Key 只放环境变量 / `.env`（`.gitignore`）。 |

## 15. 诚实清单（**主动说，比被问出来强**）

1. **退避是简版的**：流式仅首字节前重放，中途失败不重试；两处都无 jitter、无熔断。
2. **真实网络超时→退避的端到端没有假上游测试**：策略在单测里逐分支钉住，但没有真超时的集成断言。
3. **`MockAiAdapter` 是关键词驱动的桩**，只用于无 Key 演示，不理解真实语义。
4. **E2E 只跑 Chromium**，且助手走离线桩。
5. **前端两层测试（L5/L6）未接入 CI**（仓库暂无 CI 配置）。
6. **Compose 只起单实例**：确认态并发去重靠行锁（多实例成立），但没压测；Run 的"唯一 RUNNING"不变量只在进程内保证，多实例会破。
7. **停止只掐得断流式那一路**：阻塞回合（`POST /{id}/messages`）没有中途 abort 的钩子。
8. **服务端渲染的措辞固定中文**：提示词已改为"用顾客的语言回答"，模型自己的话会跟着切换，但 `ToolReport` 渲染的那几行（「你名下有 N 张订单：」、状态标签）不会。改动前落库的历史消息仍是旧格式 `[工具名] {JSON}`，机器文本通道已删，它们以普通正文呈现。

> 主动报缺口不扣分；被问出来又说不出边界才扣。

## 16. 现场操作速查与故障预案

```bash
# 起库 + 起应用（端口 8081）
docker compose up -d mysql
export JAVA_HOME="$HOME/.jdks/temurin-17/Contents/Home"
cp .env.example .env                     # 填入 AI_API_KEY（或 DASHSCOPE_API_KEY）

make test            # 后端（需常驻 MySQL，测试库 ordermgt_test）

```

**常见故障预案**：
- 启动即失败 → 常驻 MySQL 没起（默认 profile `mysql`，连 `localhost:3306/ordermgt`）。
- `Migration checksum mismatch` → 改过已发布的迁移文件；`docker compose down -v && make db-up` 整卷重建。
- 助手调不通 → 没有 Key 或 Key 失效；切 `offline` profile 演示。
- 页面停在登录页 → 没登录或会话过期；用 `1001`/`1111` 登录。

## 附：可能被问、文档里没写的点（预案）

- **"为什么用 MyBatis-Plus 而不是 JPA？"**：对"分页 + 手写 SQL + 行锁"更直接，`FOR UPDATE` 不用绕 JPQL。
- **"MapStruct 和 Lombok 怎么共存？"**：需要 `lombok-mapstruct-binding`（已在父 POM 配好）。
- **"SSE 为什么用 `fetch` 不用 `EventSource`？"**：`EventSource` 不能设请求头，而要带 CSRF 头、要带会话 cookie。
- **"前端为什么不用 router / Pinia？"**：这个规模引入只会增加讲解负担；tab 切换一个 `ref` 就够。Pinia 记为升级路径。
- **"uptime / 可观测？"**：`/actuator/health`、`ai_invocations` 审计表、`GET .../invocations`。

## 附：上场卡（A4）

```
一句话：AI 提议、人确认、服务端校验、价格由服务端决定；因为 AI 输出是不可信输入。

分层：api → application → domain ← infrastructure（domain 零框架）

一次请求九步：身份收窄 → 排队 → 先落客户消息 → 开 Run → 事务外调模型
             → 按 mutating 分流（只读执行/变更落卡）→ done + 审计行

必答：
 1 审批闸口：internalToolExecutionEnabled(false) + 白名单 + AssistantService 没有变更路径
 2 AI 不进事务：AssistantService / IdempotencyGuard 无事务；OrderService / ActionConfirmationService 有
 3 价格：schema 无价格字段，catalog 解析；grounding 修 sku 幻觉
 4 幂等两条路：INSERT 撞唯一键（客户端）+ FOR UPDATE 行锁（重复确认）
 5 解耦：AiAssistantPort 端口 + MockAiAdapter 离线桩
 6 身份：会话 cookie（PIN 登录）+ CSRF，不信任任何客户端身份头
 7 回复：只读结果由服务端渲染成人话进 transcript，原始 JSON 只留在审计侧（ADR-0015）

诚实清单背熟的 3 条：退避简版无熔断 / 超时无语义端到端测试 / 停止只对流式有效
```
